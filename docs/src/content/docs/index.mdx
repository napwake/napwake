## See what's idle first

A team that works 10 hours a day, five days a week, uses staging 50 of 168 hours. The other 70%, it's idle. `kubectl napwake scan` shows your cluster's own number before you install anything in it.

Install the plugin first, with Homebrew or [another way](/getting-started/kubectl-plugin/#installation).

<ScanShowcase>

```sh
brew install napwake/tap/kubectl-napwake
kubectl napwake scan
```

</ScanShowcase>

## Four states, four doors

<Cards even>
  <StateCard state="asleep">Scaled to zero. Its Services are routed to the doorman, which wakes it on the first request.</StateCard>
  <StateCard state="waking">A request, an activity annotation, or `autoResume` ahead of demand woke it. Its replicas are restored and its dependencies woken.</StateCard>
  <StateCard state="awake">Its pods are Ready and held requests passed through. With no activity for `idleAfter`, and no forecast of demand, it pauses again.</StateCard>
  <StateCard state="error">Something stops Napwake doing its job, and `kubectl napwake status` says what to fix. Its door has a note pinned on it.</StateCard>
</Cards>

## How it works

Label a Deployment, StatefulSet or namespace `napwake.dev/managed: "true"` and Napwake creates a ManagedWorkload for it, with its settings from annotations. Then it keeps an activity clock, fed by CPU, deploys, activity annotations and Prometheus.

:::note[Private or public]
Napwake is for non-production environments on your own clusters. Behind a VPN, SSO or an allowlist, the first request wakes a paused workload.

Public ones can ask first. A browser gets a **Wake it** button, and crawlers, scanners and API calls wake nothing. [Public preview environments](/guides/preview-environments/) says how.
:::

## Quick example

```yaml title="deployment.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-api
  namespace: dev
  labels:
    napwake.dev/managed: "true"
  annotations:
    napwake.dev/dry-run: "true"
    napwake.dev/idle-after: "1h"
```

Napwake watches `my-api` and records each time it's active. Activity is CPU above `cpuThreshold` (10% of its requests by default), a deploy or an activity annotation. With a [Prometheus query](/guides/prometheus-signals/), it's also the request rate.

In dry-run it only measures. Once you run `kubectl napwake enable my-api -n dev`, it pauses the Deployment after an hour with no activity. It wakes it when a request reaches its Service.

For every setting, see [Opting in](/guides/opt-in/). For settings annotations don't cover, write a [ManagedWorkload](/guides/managed-workload/) yourself.
