## Every command

The request limit and the connection flags every command shares. [Namespaces and connections](/getting-started/kubectl-plugin/#namespaces-and-connections) says which namespaces each command reads.

| | |
|---|---|
| Each request to the API server | Gives up after 30 seconds, so a cluster that stops answering ends a command with an error |
| `--request-timeout` | Changes that limit. Its `0` keeps 30 seconds, where kubectl's means no limit |

Every command takes kubectl's connection flags:

`--kubeconfig`, `--context`, `--cluster`, `--user`, `--as`, `--as-group`, `--as-uid`, `--token`, `--server`, `--certificate-authority`, `--client-certificate`, `--client-key`, `--insecure-skip-tls-verify`, `--tls-server-name`, `--proxy-url`, `--username`, `--password`, `--disable-compression` and `--request-timeout`.

The two commands with no section of their own:

| Command | What it does |
|---|---|
| `version` | Prints the plugin's version. It needs no operator |
| `completion` | Writes a shell completion script, for bash, zsh, fish or PowerShell |

## `scan`

Its flags, with their defaults. [Scan a cluster](/getting-started/kubectl-plugin/#scan-a-cluster) shows it in use.

| Flag | Default | What it does |
|---|---|---|
| <Ref id="scan-namespace" name="--namespace" /> `-n` | all you can read | Namespace to scan. Repeat for several |
| <Ref id="scan-all-namespaces" name="--all-namespaces" /> `-A` | `false` | Every namespace, failing rather than falling back. Not with `-n` |
| <Ref id="scan-exclude-namespaces" name="--exclude-namespaces" /> | `kube-system`, `kube-public`, `kube-node-lease` | Namespaces to skip |
| <Ref id="scan-output" name="--output" /> `-o` | `table` | `table`, `json` or `yaml` |
| <Ref id="scan-limit" name="--limit" /> | `25` | Rows in the table, idle first, then paused, then active, each by what pausing could free |
| <Ref id="scan-cpu-threshold" name="--cpu-threshold" /> | `10` | CPU use above which a workload is active, as a percentage of requests. From 0.1 to 100, such as `10` or `0.5` |
| <Ref id="scan-cpu-price" name="--cpu-price" /> | `0.031` | Your price per vCPU-hour, in dollars, zero or more, for every workload. Unset, each node is priced at its type's list price, and one with none at AWS on-demand in us-east-1 |
| <Ref id="scan-memory-price" name="--memory-price" /> | `0.004` | Your price per GiB-hour of memory, in dollars, zero or more, for every workload. Unset, each node is priced at its type's list price, and one with none at AWS on-demand in us-east-1 |
| <Ref id="scan-window" name="--window" /> | `7d` | Prometheus history to replay, such as `7d` or `36h`, up to `366d`. `0` judges from CPU now |
| <Ref id="scan-idle-after" name="--idle-after" /> | `1h` | Time without activity that makes a workload idle, as Napwake's `idleAfter` |
| <Ref id="scan-prometheus-service" name="--prometheus-service" /> | the one in the cluster with the most history | Prometheus Service in the cluster, as `namespace/name` or `namespace/name:port`, read through the API server |
| <Ref id="scan-prometheus-url" name="--prometheus-url" /> | the one in the cluster with the most history | Prometheus API to read, such as Thanos, Mimir, or Google Cloud Managed Service for Prometheus |
| <Ref id="scan-prometheus-selector" name="--prometheus-selector" /> | | Label matchers added to every history query, such as `'cluster="prod"'`, for a Prometheus of several clusters |
| <Ref id="scan-prometheus-header" name="--prometheus-header" /> | | Header for `--prometheus-url`, as `"Name: value"`, such as `"X-Scope-OrgID: tenant"` for Mimir. Repeat for several |
| <Ref id="scan-prometheus-bearer-token-file" name="--prometheus-bearer-token-file" /> | | File holding a bearer token for `--prometheus-url` |
| <Ref id="scan-prometheus-ca-file" name="--prometheus-ca-file" /> | | PEM file of CA certificates to trust for `--prometheus-url`, besides the system's |
| <Ref id="scan-prometheus-insecure-skip-verify" name="--prometheus-insecure-skip-verify" /> | `false` | Don't verify `--prometheus-url`'s certificate |
| <Ref id="scan-timeout" name="--timeout" /> | `5m` | How long the scan may take before it gives up |
| <Ref id="scan-html" name="--html" /> | a temporary file | Save the web report to this file, to share |
| <Ref id="scan-open" name="--open" /> | `true` | Open the web report, when the table is shown in a terminal |

<section id="scan-flags-more">

### More on the flags

`--limit 0` lists every workload. `--limit` also caps the dependency list, and JSON and YAML list everything.

`--cpu-threshold` and `--idle-after` apply now and in the replay. Workloads Napwake manages use their own settings. JSON and YAML give each workload's as `idleAfter`.

`--prometheus-selector` values are double-quoted, as in PromQL.

</section>

<section id="scan-columns-more">

### More on the first line and the columns

JSON and YAML keep the full context name. Their `namespaces` counts every namespace read.

`Your bill:`, under the first line, says what turns what pausing frees into savings. It's from the node autoscaler [`nodes`](#nodes-autoscaler) finds (JSON `nodeAutoscaler`).

| The node autoscaler | `Your bill:` says |
|---|---|
| Karpenter, Cluster Autoscaler or EKS Auto Mode | It `drops only as` it `removes nodes` |
| Karpenter | The same, with how its NodePools consolidate |
| Cluster Autoscaler, hinted at only by a Deployment | The same, and that it may not be running |
| GKE Autopilot, which bills what pods request | It `drops as pods stop` |
| None found | It `won't drop until something removes nodes`, with the guide to setting an autoscaler up |
| Your access doesn't allow reading what would tell | It says so, and names what it couldn't read |

What the columns count, and leave out:

| Case | What the scan does |
|---|---|
| COST/HOUR | Shown when it judges from CPU now, with no Prometheus it can reach or `--window 0`. What the workload's requests cost an hour while running, to the cent, and `<$0.01` under one. Each hour paused frees that. COST/MO is it times 730 (JSON `hourlyCost` and `monthlyCost`) |
| COULD FREE/MO | Never calls it a saving. Before Napwake runs, the scan can't know what of it would be saved |
| Each money and history cell | Has the one source the table gives |
| A live workload | Isn't replayed, as there are no pods for Prometheus to record while it's paused. Its pauses are what FREED THIS MONTH and SAVED count |
| A StatefulSet that deletes its PVCs when scaled down | Would lose its data to a pause, so Napwake refuses to pause it. It's left out of what pausing could free and of the next steps |
| A protected workload | Left out of what pausing could free and the next steps |
| Which are protected | Those labelled `napwake.dev/protected`, and those matching a built-in pattern (`kube-*`, `openshift-*`, `cattle-*`, `gke-*`, `gmp-*`). The operator's own `protectedNamespaces` patterns show only through a managed workload's `Protected=True` |
| A workload scaled to zero by hand | Counted apart in the headline. It counts toward nothing the scan says could be freed |

</section>

<section id="scan-idle">

### How it decides a workload is idle

It uses the signals Napwake uses to pause.

| Workload | How it's judged |
|---|---|
| Managed by Napwake | By the activity clock Napwake keeps for it. Idle is no activity until the clock's `pauseAt`. That's `idleAfter` after the last activity, or longer after [pauses made in use](/concepts/idle-detection/#paused-while-in-use) |
| Managed, after pauses made in use | BECAUSE says so, such as `not idle yet: it woke 6m ago; after pauses made while it was in use, it waits 20 minutes, not 5 minutes` |
| Managed, its activity clock | Combines every source configured, Prometheus queries too |
| Managed, held awake | The scan says so, such as for its dependents |
| Managed, its clock started without activity | BECAUSE says what started it |
| Started by a wake | `not idle yet: it woke 3m ago` |
| Started as Napwake took it on | `not idle yet: Napwake began managing it 3m ago` |
| Started by a [gap in watching](/concepts/idle-detection/#restarts-and-outages) | `not idle yet: Napwake wasn't watching until 3m ago` |
| Any other, active | CPU above `--cpu-threshold` (10% by default) of what it requests |
| Any other, active | A rollout within `--idle-after` (1h by default) |
| Any other, active | A `napwake.dev/last-activity` annotation within `--idle-after` |
| Any other, active | A `napwake.dev/active-until` in the future |
| Any other, idle | None of those, with its CPU measured |
| Unmanaged, without metrics-server | As on EKS by default. Judged from its CPU history, and BECAUSE says so |
| Its state then | Where the replay left the activity clock |
| No CPU requests, or no metrics yet | Can't be judged. It's in the notes, not the table, and out of the headline's totals |

</section>

<section id="scan-notes">

### What the notes list, and what the scan leaves out

| In the notes | What it means |
|---|---|
| Replicas set from Git | A GitOps tool last set the workload's replicas, by the field managers the API server records |
| Which tools | Argo CD, Flux, Fleet, kapp or Kluctl. Workloads are listed by tool |
| Why it matters | The tool would undo every pause until told, once, to leave replicas to Napwake. See [GitOps tools](/guides/gitops/) |
| Once the tool is told | The workload isn't listed |
| For Argo CD | The scan reads that from the Application and `argocd-cm`, as [`enable`](#enable) does |
| Without access to them | The note says so, and lists the workload to check |
| In JSON | The tool in `replicasFromGit`, `gitOpsLeavesReplicas` once told, and `gitOpsUnchecked` for why it couldn't check |
| In the next steps | Never suggested, as the tool would revert a label put on by hand too |
| The cluster's own infrastructure | Left out of the table, the totals and the next steps. A note counts it by namespace |
| Infrastructure in JSON and YAML | Listed in `platform`, each with what it is |

| Left out | Found by |
|---|---|
| Kubernetes' and platforms' namespaces, never paused | `kube-*`, `openshift-*`, `cattle-*`, `gke-*` and `gmp-*` |
| Napwake's namespace, never paused | Its Deployment's `app.kubernetes.io/name: napwake` label |
| The operator's and the doorman's Deployments, never paused | `control-plane: controller-manager` or `control-plane: doorman`, in any namespace |
| The same, also needed | `app.kubernetes.io/name: napwake`, or a `napwake` `helm.sh/chart` label |
| What the scan guesses nobody means to pause | Well-known kinds, such as ingress controllers, cert-manager, Vault, Argo CD, Flux, service meshes, policy engines and monitoring |
| The same, by namespace | `ingress-nginx`, `cert-manager`, `vault`, `argocd`, `flux-system`, `istio-system`, `linkerd`, `gatekeeper-system`, `kyverno`, `monitoring` and others |
| The same, by label | `app.kubernetes.io/name`, `app.kubernetes.io/part-of`, `app`, `k8s-app` or `helm.sh/chart` |
| Workloads labelled `napwake.dev/ignore=true` | They aren't listed at all |

What leaving them out changes:

| Left out | What changes |
|---|---|
| What Napwake never pauses | Apps' dependencies on it aren't listed, as Napwake never needs to wake it |
| The guessed infrastructure | Left out of the estimate only. The operator has no such rule |
| The same, opted in | Napwake pauses it like any app, so dependencies on it are listed |
| No guessing | For a workload Napwake manages, or in a namespace labelled `napwake.dev/managed=true`, such as a preview with its own Vault |
| A namespace labelled `napwake.dev/allow-protected=true` | Scanned like any other, apart from Napwake's own Deployments |

</section>

<section id="scan-history">

### History from Prometheus

With a Prometheus in the cluster, the scan replays each workload's last week of CPU and rollouts. It runs Napwake's activity clock over them, as if managing it with `--idle-after` and `--cpu-threshold`.

| | How it works |
|---|---|
| Finding it | By the Services the Prometheus Operator (so kube-prometheus-stack) and the community Helm chart create |
| Reaching it | Through the API server's service proxy, so there's no port-forward or URL to give |
| Naming it | The `History:` line and the report's subtitle (JSON `history.prometheus`) |
| How much was replayed | On the same line and subtitle (JSON `history.hours`) |
| Several | It reads the one with the most of the window's CPU history, ranked as below |
| How many | It tries five at most. The `History:` line lists the others (JSON `history.others`) |
| `--prometheus-service namespace/name` | Reads that Service instead, found or not, through the API server |
| Its port | Its API port, or the one you add, as in `monitoring/thanos-query:http` |
| `--prometheus-url` | Reads one outside the cluster, such as Thanos or Mimir. See [A Prometheus elsewhere](#a-prometheus-elsewhere) |
| Either, unreadable | The scan fails, rather than going on without history |
| CPU | Per container, from cAdvisor's `container_cpu_usage_seconds_total`, which every common setup scrapes |
| Steps | Five minutes, coarser for windows over about 34 days |
| Pods | Matched to their workload by name |
| A Deployment's pods | Those of deleted ReplicaSets too, named `<deployment>-<hash>-<suffix>` |
| A long Deployment name | If Kubernetes cut its pods' names short, only current ReplicaSets' pods are replayed |
| Sidecars | Those added at pod creation are left out of activity, as for the activity clock |
| An active step | A rollout, or the workload's own CPU above the threshold of its running pods' requests, as the operator counts it |
| After `--idle-after` with none | It sleeps until the next active step, which is one wake |
| CPU within 15 minutes of a pause, or within `--idle-after` if that's shorter | Shows it was in use |
| Each such pause in a row | Doubles the next wait, up to `--idle-after` plus an hour, as Napwake does after [a pause made in use](/concepts/idle-detection/#paused-while-in-use) |
| A pause that lasts past that window | Ends the longer wait |
| A rollout | Wakes it, without counting either way |
| What it can't see | Requests and activity annotations, which aren't in Prometheus. It sees only CPU and rollouts |
| So | A workload used with little CPU can look like it would sleep more than it would |
| Requests and prices | Today's |

| Rank | Preferred |
|---|---|
| 1 | cAdvisor's container CPU from the window's start, then any CPU, then any that answers |
| 2 | A monitoring namespace, in order `monitoring`, `prometheus`, `observability`, `kube-prometheus-stack`, `cattle-monitoring-system`, `openshift-monitoring` |
| 3 | A usual name, in order `prometheus-operated`, `kube-prometheus-stack-prometheus`, `prometheus-server`, `prometheus`, `prometheus-k8s` |
| 4 | The Prometheus Operator's Service over the community chart's |
| 5 | The first by namespace and name |

| Time and short history | What happens |
|---|---|
| History's share | The first 60% of `--timeout`, so a slow Prometheus or Thanos can't use up the scan |
| A namespace's reads | Its API reads come before its history query, sharing that time |
| Once it's spent | A namespace reached after that isn't queried |
| A slow query | It may take whatever is left, however long. `--request-timeout` doesn't cut it short |
| Not read in time | Judged from CPU right now. The notes name these namespaces |
| The notes' advice | A longer `--timeout` gives history more time, or `--window 0` skips it |
| A query given up with time left | By Prometheus or the API server's proxy. The notes name the namespaces, and suggest a shorter `--window`. A longer `--timeout` wouldn't help with it |
| Less history than the window | The replay covers what there is, and says how much, such as "Replaying the last 30 minutes" |
| The same, in the notes | A note says it's shorter than asked |
| Under a day | It can't show a day's pattern. The headline says so, in the terminal and the report |
| The headline's advice | Scan again after a few days |
| No Prometheus, or no permission to reach it | The scan judges from CPU right now, and says why |

</section>

### A Prometheus elsewhere

`--prometheus-url` reads a Prometheus API your machine can reach, rather than one in the cluster. It needs no cluster permission at all. If it doesn't answer like a Prometheus API, the scan fails rather than going on without history.

| Store or need | What to do |
|---|---|
| A store of several clusters, such as Thanos or Mimir | Pass `--prometheus-selector` with the label that tells them apart |
| The notes' hint | They suggest it when they see series from more than one source |
| Authentication | `--prometheus-header`, such as `X-Scope-OrgID` for a Mimir tenant, or `Authorization` |
| Or | `--prometheus-bearer-token-file`. Not both for one header |
| Its certificate | `--prometheus-ca-file` and `--prometheus-insecure-skip-verify` |
| A Prometheus in the cluster | These flags don't apply. It's reached through the API server, with your kubeconfig |
| Google Cloud Managed Service for Prometheus | GKE's keeps its data in Cloud Monitoring, so the scan doesn't find it |
| Its collectors | In `gmp-system`, with nothing to query. The scan reads another Prometheus if the cluster has one |
| To read it | Give it an access token, and name your project and cluster, as below |
| Its frontend, deployed in the cluster | `--prometheus-service NAMESPACE/frontend` reads through that, with the frontend's credentials |
| Either way | The replay's CPU is there only if it collects cAdvisor's metrics |
| Turning those on | `kubeletScraping` in its OperatorConfig |
| Amazon Managed Service for Prometheus | It needs SigV4 signing, which the scan doesn't do. Point `--prometheus-url` at a signing proxy |

Name the cluster too, since the store holds every cluster in the project.

```bash
kubectl napwake scan \
  --prometheus-url https://monitoring.googleapis.com/v1/projects/PROJECT_ID/location/global/prometheus \
  --prometheus-bearer-token-file <(gcloud auth print-access-token) \
  --prometheus-selector 'cluster="CLUSTER_NAME"'
```

<section id="scan-headline">

### The headline's counts

| Count | What it counts |
|---|---|
| `pausing 14 live workloads` | Only live workloads Napwake pauses |
| Its money | What they freed, and what any put back in dry-run freed while live |
| With none live | It says the money came from workloads since put back in dry-run, if there are some |
| Put back in dry-run | A workload keeps what it freed and saved while live |
| Would-be pauses | Never add to what's freed or saved |
| Protected live workloads | A line of their own, with what they freed this month before protection, if anything |
| `0 of 13 unmanaged workloads would have slept` | Unmanaged workloads replayed |
| `Not counted:` | Listed workloads the replay count leaves out, and why, as the report's summary does |
| Not counted, won't pause | `1 that won't pause (PVCs deleted on scale-down)` |
| Not counted, the others | Those in protected namespaces, scaled to zero by hand, or without CPU history |

The protected line reads like this. Its workloads are in a protected namespace, part of Napwake, or StatefulSets deleting PVCs on scale-down (`Protected=True`).

```text
1 more live workload is protected, so Napwake never pauses it; it freed $12 this month before it was, and saved $5 of that.
```

JSON gives `totals.live` and `totals.liveProtected`. It also gives `totals.protectedFreedThisMonth` and `protectedSavedThisMonth`, which are part of `freedThisMonth` and `savedThisMonth`.

</section>

| | How it reads them |
|---|---|
| An address | It names a Service in a scanned namespace, in any form cluster DNS gives it |
| Its forms | `postgres`, `postgres.preview-42`, `postgres.preview-42.svc.cluster.local`, or a headless Service's pod, `postgres-0.postgres-hl` |
| Where | In a URL, a `host:port`, or a list of either |
| The workload | The one the Service's selector picks |
| Not an address | A bare word on its own, such as `MODE=postgres` |
| Names | Variable names don't matter. Service names come from the cluster, not a list the scan keeps |
| Shown | Only its scheme, host and port, such as `postgres://postgres:5432` |
| Hidden | A user, password, path and query string, any of which could hold a credential |
| In the terminal | The variable it was found in. Only JSON and YAML carry the address |
| Secrets | Never read, so addresses there aren't found. The notes name workloads that take variables from Secrets |
| Code and files | Addresses built in code or read from files aren't found either |

When Napwake manages both, it wakes a dependency with the workload that needs it. It keeps it up while that workload is, so the first request doesn't wait for it too ([Dependencies](/concepts/dependencies/)).

| Last column | When |
|---|---|
| `woken with it once both are managed` | Napwake doesn't manage the workload yet |
| `not managed, so never paused` | Napwake doesn't manage the dependency, which stays up anyway |
| `woken and held with it` | Learned from the workload's environment, or a wake |
| `declared; woken and held with it` | Declared with `napwake.dev/depends-on` |
| `not learned yet` | Napwake manages it, but hasn't learned it |

Before Napwake manages any workload that needs them, every dependency would say the first. So the scan and the report say it once above the list, and leave the column out.

### Turned away while asleep

Under the table, when a workload that asks before waking turned requests away in its current or last pause:

A person shown the asleep page isn't counted. So many mean something automated calls it, such as a monitor, a webhook or another service. `-o json` has them as `turnedAway`, from the ManagedWorkload's `status.turnedAway` ([What it turns away](/concepts/wake-on-request/#what-it-turns-away)).

Under the table, each ingress-nginx Ingress in front of a workload that waits less than its `wake.maxWait`:

```text
Behind ingress-nginx, which answers a write held longer than it waits with a 504, if a wake takes that long:
  preview-42/api   Ingress api waits 60s, maxWait is 120s
  preview-42/web   Ingress web waits 60s, maxWait is 120s. Its proxy-read-timeout "120s" isn't whole seconds, so ingress-nginx ignores it: write "120"
```

ingress-nginx ignores a `proxy-read-timeout` that isn't whole seconds, such as `"120s"`, and waits its default. That Ingress's line says so, and what to write.

It's a note, not a problem, since most wakes take seconds. Once a wake by a request has taken longer, `IngressTimeoutShort` lists it under Needs attention instead. It's read from the ManagedWorkload's `status.nginxIngresses`, recorded once it has paused ([A wake that outlasts ingress-nginx's timeout](/concepts/wake-on-request/#a-wake-that-outlasts-ingress-nginxs-timeout)).

### Recent pauses and wakes

| Recent pauses and wakes | |
|---|---|
| A wake's cause | A request on a Service, an activity annotation, a wake request, the forecast, or a scale-up from outside Napwake |
| Activity annotations | Including a dependent waking |
| Wake requests | From `kubectl napwake wake`, or a tool setting `napwake.dev/wake-requested`, by their `WakeRequested` event |
| Requests the doorman closed without reaching the workload | Listed too |
| A wake with no recorded cause | Listed by its `resumed` event alone, such as a hand-back when a namespace becomes protected |
| How many | The table shows the latest 10, and `-o json` every one |
| Each one's `kind`, in `-o json` | `pause`, `wake` or `notServed` |
| `wokenBy`, in `-o json` | On each wake. Each workload carries it too, for its latest wake until it pauses again |
| `wokenBy` left out | When the cause wasn't recorded, and once the events have expired |
| A ManagedWorkload deleted and made again under the same name | Starts without one, since the old one's events name its UID, not the new one's |
| How far back | The API server keeps events for an hour, unless its `--event-ttl` says otherwise. So on most clusters, an hour is what `status` can show |

| `wokenBy` | What woke it |
|---|---|
| `request` | A request on one of its Services, through the doorman, including a person's click on one that asks first |
| `activity` | An activity annotation, a dependent waking, or a Prometheus activity query |

| `forecast` | `autoResume`, ahead of the demand the forecast expects |
| `outside` | A scale-up from outside Napwake |
| `pauseCancelled` | Whatever came as it paused, which the event's message names |

| Field | What it holds |

## `pause`

Its flags, with their defaults. [Pause a workload](/getting-started/kubectl-plugin/#pause-a-workload) shows it in use.

| Flag | Default | What it does |
|---|---|---|
| <Ref id="pause-namespace" name="--namespace" /> `-n` | your kubeconfig context's | Namespace of the workload |
| <Ref id="pause-wait" name="--wait" /> | `true` | Wait until it's Paused, or Napwake says why not |
| <Ref id="pause-yes" name="--yes" /> `-y` | `false` | Pause even if the forecast expects it busy within the hour, without asking |
| <Ref id="pause-clear-hold" name="--clear-hold" /> | `false` | Clear a `napwake.dev/active-until` hold, on its ManagedWorkload, as `wake --for` sets it, or on the workload, without asking |
| <Ref id="pause-timeout" name="--timeout" /> | `5m` | How long to wait, cluster calls included. It starts again after you answer a question |

With [`wake: ask`](/concepts/wake-on-request/#asking-before-waking), its answer says a person's click on the asleep page, or `kubectl napwake wake`, wakes it, not a request. On a ManagedWorkload Napwake hasn't taken on yet, such as one created a moment ago, `pause` waits until Napwake has. A request already on it then isn't acted on.

<section id="pause-forecast">

### When the forecast expects it to be busy

When a confident forecast expects the workload busy within the hour, Napwake declines the pause and says when. It would likely be woken straight back, so `pause` asks.

<TerminalBlock
  label="pause asking whether to override the forecast"
  output={[
    "preview-42/api wasn't paused: the forecast expects demand at 80% of requests in the hour from 09:00 UTC",
    "Pause it anyway? [y/N]",
  ]}
/>

| Answer or case | What happens |
|---|---|
| `y` | It asks again, overriding the forecast, and it pauses |
| Anything else | It stays running, and `pause` exits 0 |
| Taking your time | The question waits as long as you take |
| `--timeout` | Counts only time on the cluster, and starts again after your answer |
| `--yes` | Overrides the forecast from the start, without asking |
| No terminal, as in a script | `pause` exits 1 with the reason, and says to pass `--yes` |

</section>

<section id="pause-hold">

### When something holds it awake

A `napwake.dev/active-until` annotation holds it awake, on the ManagedWorkload, as `wake --for` sets it, or on the workload. Napwake would refuse the pause, so `pause` asks first, naming which holds it.

<TerminalBlock
  label="pause asking whether to clear a hold"
  output={[
    "preview-42/api wasn't paused: the napwake.dev/active-until annotation on its ManagedWorkload keeps it awake until 2026-10-17T20:00:00Z",
    "Clear it and pause now? [y/N]",
  ]}
/>

| Answer or case | What happens |
|---|---|
| `y` | It removes the annotation, from both if both hold it, and pauses |
| Anything else | It stays running, and `pause` exits 0 |
| `--clear-hold` | Clears it without asking |
| No terminal, without `--clear-hold` | `pause` exits 1, and says to pass it |
| `--yes` | Doesn't clear a hold |

So a nightly script that pauses with `--yes` doesn't end a hold someone set for a demo.

</section>

<section id="pause-gitops">

### When a GitOps tool sets its replicas

A GitOps tool may set the replicas from Git, without being told to leave them to Napwake. Then `pause` warns before asking, with the one-time fix. [GitOps tools](/guides/gitops/#checking-the-fix-is-in) says how it tells.

<TerminalBlock
  label="pause warning that a GitOps tool would undo the pause"
  output={[
    "Warning: Argo CD application argocd/shop sets preview-42/api's replicas from Git, as argocd-controller, so its next sync will likely scale it back up, undoing this pause. To have Argo CD leave replicas to Napwake, once:",
    "  Add RespectIgnoreDifferences=true to the syncPolicy.syncOptions of Argo CD application argocd/shop, so syncs leave the replicas it ignores.",
    "See https://docs.napwake.dev/guides/gitops/#argo-cd",
  ]}
/>

When it can't tell, such as without access to Argo CD's namespace, the warning says why. It says to make the fix if you haven't.

</section>

<section id="pause-permissions">

### Permissions

| Your user needs | For | Without it |
|---|---|---|
| `get`, `list` and `patch` on `managedworkloads` in the namespace | The pause | |
| `get` on the workload | The GitOps warning, and the workload's own hold | They're left out |
| `patch` on the workload | Clearing a hold on it | |
| `get` on the `argocd-cm` ConfigMap | Telling whether Argo CD leaves its replicas | The warning says it couldn't check |
| `list` on `applications.argoproj.io` in every namespace, or `get` in `argocd` | The same | The same |

The Argo CD reads are only for a workload Argo CD applies.

</section>

## `wake`

Its flags, with their defaults. [Wake a workload](/getting-started/kubectl-plugin/#wake-a-workload) shows it in use.

| Flag | Default | What it does |
|---|---|---|
| <Ref id="wake-namespace" name="--namespace" /> `-n` | your kubeconfig context's | Namespace of the workload |
| <Ref id="wake-for" name="--for" /> | | Also keep it awake this long, by setting `napwake.dev/active-until` on its ManagedWorkload. A hold there that ends later stays, and `wake` says so |
| <Ref id="wake-wait" name="--wait" /> | `true` | Wait for Napwake's answer to the request, then until it's Running |
| <Ref id="wake-timeout" name="--timeout" /> | `5m` | How long to wait, cluster calls included |

`wake` sets a fresh `napwake.dev/wake-requested` value on the ManagedWorkload, as any tool can. So it wakes the workload whatever its wake setting.

The `WakeRequest` condition says what came of it ([Wake now](/guides/pause/#wake-now)). Another tool asking meanwhile replaces `wake`'s token with its own, and Napwake's answer to that one stands for both.

| When | `wake` |
|---|---|
| Napwake refuses the request, such as for a protected workload | Fails at once with Napwake's reason, without waiting out `--timeout` |
| Napwake doesn't answer by `--timeout` | Fails with its phase, saying Napwake hasn't taken the request up. That usually means its operator isn't running |
| The ManagedWorkload is deleted meanwhile | Fails, saying Napwake handed the workload back as it let go |
| A slow start | `--timeout` covers the answer and `Running`. A request made as the workload pauses is answered at once, and calls the pause off. One made as it wakes is answered only once the wake finishes. For a start over 5 minutes, raise it, such as `--timeout 10m` |

<section id="wake-permissions">

### Permissions

Your user needs `get`, `list` and `patch` on `managedworkloads` in the namespace.

</section>

## `enable`

Its flags, with their defaults. [Enable a workload](/getting-started/kubectl-plugin/#enable-a-workload) shows it in use.

| Flag | Default | What it does |
|---|---|---|
| <Ref id="enable-namespace" name="--namespace" /> `-n` | your kubeconfig context's | Namespace of the workload |
| <Ref id="enable-all" name="--all" /> | `false` | Enable every workload in the namespace |
| <Ref id="enable-force" name="--force" /> | `false` | Change the cluster even when a GitOps tool applies the setting from Git |
| <Ref id="enable-timeout" name="--timeout" /> | `1m` | How long to wait for the cluster before giving up |

<section id="enable-refuses">

### When it changes nothing

`enable` only ends dry-run for a workload Napwake manages. Otherwise it changes nothing, and exits non-zero with the reason.

| Reason | What it means |
|---|---|
| The namespace is protected | Labelled `napwake.dev/protected=true`, or a `kube-*`, `openshift-*`, `cattle-*`, `gke-*` or `gmp-*` namespace |
| Unless | It's labelled `napwake.dev/allow-protected=true` |
| The workload is left out | Labelled `napwake.dev/ignore=true` |
| Or opted out | Its own `napwake.dev/managed` is anything but `"true"`, in a managed namespace |
| No ManagedWorkload manages it | The operator isn't running, doesn't watch the namespace, or protects it by its own settings |
| Right after you label it | Its ManagedWorkload may not exist yet. Run `enable` again a few seconds later |
| Its ManagedWorkload says Napwake never pauses it | `Protected=True`, a target labelled `napwake.dev/ignore`, or `DuplicateTarget=True` |
| `Protected=True` | Such as by a `protectedNamespaces` pattern, or for Napwake's own operator and doorman |
| No ManagedWorkload CRD | It says Napwake isn't installed |

</section>

<section id="enable-all-namespace">

### With `--all`

`--all` ends dry-run for every workload in the namespace.

| When | What it does |
|---|---|
| The namespace's own `napwake.dev/dry-run`, or the cluster default, keeps any in dry-run | Sets the namespace's annotation to `"false"` |
| The same | Drops the workloads' own annotations, so the namespace decides for all |
| Each is in dry-run by its own annotation | Leaves the namespace alone, and sets each workload's to `"false"` |
| Either way | Sets `spec.dryRun: false` on ManagedWorkloads written by hand in the namespace |
| Git owns the namespace | Leaves its annotation for you to change in Git, ending dry-run for workloads that take it |
| The same | Workloads with their own annotation get `"false"` |
| You can't change the namespace, as with `edit` or `admin` bound in it | Leaves its annotation, and says so |
| The same | Sets every workload's own to `"false"`, which wins over it |
| The same, with only the namespace's to change | Exits non-zero |
| Labelled workloads no ManagedWorkload manages | Left alone |
| The same, after `enable` set the namespace to `"false"` | Their dry-run ends once Napwake picks them up, unless they have their own annotation |
| The rest of those | Listed, and `enable` exits non-zero |
| None of the namespace's workloads picked up yet | Changes nothing, the namespace's annotation included, and exits non-zero |
| Why | The operator may not be running |
| Workloads Napwake never pauses, by their ManagedWorkload | Left alone, and listed too |

</section>

<section id="enable-gitops">

### When a GitOps tool or Helm applies the setting

A GitOps tool would put a changed setting straight back, so `enable` changes nothing it applies. It names the tool, prints the change to make in Git, and exits non-zero.

  ]}

| | |
|---|---|
| The tools | Argo CD, Flux, Fleet, kapp and Kluctl |
