Getting started

Installation

Install the operator and the doorman with Helm. If your cluster's config is kept as Kustomize, use the Kustomize manifests. Both install the same.

  • Kubernetes v1.30+, tested in CI on 1.30 and 1.37
  • kubectl v1.30+
  • metrics-server, for pod CPU through the Kubernetes Metrics API
  • Helm v3.8+, to install the OCI chart

With Argo CD or Flux

Section titled “With Argo CD or Flux”

The chart is only in an OCI registry, which Argo CD and Flux name differently. Commit one of these where your GitOps tool syncs from.

  • Argo CD
  • Flux
  • repoURL is the registry and path without oci://, which tells Argo CD it’s OCI. chart is the chart’s name.
  • The registry is public, so Argo CD needs no credentials.
  • For the Kustomize manifests, point an Application’s path at your kustomization.
  • It needs Flux 2.6 or later, where OCIRepository is v1.
  • releaseName keeps the release napwake, as these docs call it, instead of Flux’s default, napwake-system-napwake.
  • storageNamespace keeps its Helm history beside it, where helm list -n napwake-system shows it.
  • For the Kustomize manifests, point a Flux Kustomization at your kustomization.

To upgrade, change targetRevision or tag to the new version.

Moving a Helm install to Argo CD or Flux

Section titled “Moving a Helm install to Argo CD or Flux”

Argo CD or Flux can take over a helm install where it runs, with the same values. Nothing is reinstalled or restarted, and paused workloads stay paused.

Don’t uninstall first. Doing what helm uninstall asks, stopping managing every workload, wakes every paused one. It also loses each one’s forecast and its tally of what pausing freed.

Give the tool these values, and the version in the CHART column of helm list -n napwake-system.

  • Argo CD
  • Flux

  1. Commit the Application above, with those values in valuesObject and that version as targetRevision. Argo CD finds every resource as it would make it. It shows Synced and Healthy without applying anything, so an automated sync doesn’t start.

  2. Sync it once by hand, with Sync in its UI or with kubectl, giving the Application’s sync options:

    This applies the resources and marks them as the Application’s own, with argocd.argoproj.io/tracking-id. It warns that each lacks kubectl.kubernetes.io/last-applied-configuration, which Helm doesn’t set and the sync adds.

  3. Check it’s Synced and Healthy:

  4. Delete Helm’s record of the release, its sh.helm.release.v1.napwake.v<revision> Secrets, so helm no longer acts on it:

helm list -n napwake-system no longer shows it. From now on, change the values or targetRevision in Git.

Commit the OCIRepository and HelmRelease above, with those values in values and that version as tag. Their releaseName and storageNamespace are the release’s own. So Flux’s helm-controller finds it in Helm’s storage and takes it over in place. It upgrades it to a new revision, with the same values, and deletes nothing.

helm list -n napwake-system still shows it, its chart version followed by + and the start of the chart’s digest. From now on, change it in Git, since Flux undoes a helm upgrade by hand at its next reconcile.

Time zone

Section titled “Time zone”

The forecast learns when each workload is busy, by hour of day and day of week, in the operator’s time zone. It holds off pausing before busy hours and, with autoResume, wakes workloads ahead of them.

Set Helm’s timezone value, or the operator’s --timezone flag, to your users’ IANA zone, such as Europe/London, America/New_York or Asia/Kolkata. The chart’s install notes say which zone the forecast uses.

  • UTC is the default. A team on daylight saving then finds its workloads woken an hour early or late for half the year.
  • Teams in different zones can pick the zone most of them work in, or have an install each.
  • Wall-clock alignment has the details.

To change it on a Helm install, change your values file. Then upgrade with it at the version you run, as in Keeping your settings:

The operator restarts with it. With Argo CD or Flux, change valuesObject or the HelmRelease’s values in Git.

More than one install

Section titled “More than one install”

One install per cluster is usual. Several can share one, such as one per team, if each:

  • has a namespace and a release name of its own, since the chart names its ClusterRoles and admission policies after the release
  • sets watchNamespaces, with no namespace in two installs’ lists

All but one set crds.install: false. They share the ManagedWorkload CRD, which belongs to the release that installed it and is upgraded with it. Make that one the newest Napwake. The Kustomize manifests, and so install.yaml, are a single install, in napwake-system, watching every namespace.

Each operator marks the ManagedWorkloads it takes on, and the doorman EndpointSlices it writes, with napwake.dev/operator, its namespace. Another install leaves those alone, with a ManagedByAnotherInstall warning event. So two installs watching one namespace by mistake don’t both pause and wake its workloads. The first to take each one on keeps it.

Uninstall

Section titled “Uninstall”

Stop managing workloads while the operator still runs, so it can scale paused ones back up.

  1. Remove the napwake.dev/managed label from your workloads and namespaces, in Git if they live there. Napwake deletes the ManagedWorkloads it created from them.

  2. Delete the ManagedWorkloads you wrote yourself. Each scales its workload back to the replicas it had before the pause.

  3. Remove the operator:

    This keeps the CRD, since deleting it deletes every ManagedWorkload. Once none is left, delete it yourself:

    Without Helm, delete what you applied: kubectl delete -f with the install.yaml URL, kubectl delete -k . in your kustomization, or make undeploy from a clone. These delete the CRD too, unguarded, so first check kubectl get managedworkloads -A lists none.

Caution

Removing the operator or the CRD first skips step 2’s restore. Paused workloads stay at zero replicas, and their Services still send traffic to the doorman’s deleted pods. Restore them by hand.

When helm uninstall refuses

Section titled “When helm uninstall refuses”

helm uninstall refuses while any ManagedWorkload is left. Its pre-delete hook, the <fullname>-uninstall-guard Job, first waits up to two and a half minutes for those being deleted. That lets the operator restore them and drain their doorman ports, which takes up to a minute. Then the hook lists any left and fails, before anything is removed. One deleted moments before you uninstall doesn’t hold it up.

Helm Error Above it
3, before 3.18 (such as 3.16) job napwake-uninstall-guard failed Nothing
3.18 and later job napwake-uninstall-guard failed The hook’s output
4 resource Job/napwake-system/napwake-uninstall-guard not ready The hook’s output, as one log message with its line breaks escaped

The output names the ManagedWorkloads left after the wait, says what to do and links here. After the first \n, it lists each one with the steps above. From Helm 4:

When Helm prints only the error, kubectl logs job/napwake-uninstall-guard -n napwake-system shows the output, line breaks and all, for an hour. No Helm prints it for a revision that a Helm before 3.18 wrote, as a helm rollback after a refused uninstall can. That Helm drops the hook’s helm.sh/hook-output-log-policy until a newer Helm upgrades the release.

What a refused uninstall leaves, and Argo CD
  • The release is marked uninstalling, which helm list shows only with -a, though everything still runs. Uninstalling again, once the ManagedWorkloads are gone, finishes it.
  • Until then, helm upgrade fails with has no deployed releases. helm rollback napwake <revision>, with the last revision helm history napwake lists, marks it deployed again.
  • --no-hooks skips the guard, and guard.uninstall: false drops it. Guards has what it counts and runs.
  • Argo CD 3.3 and later runs the guard as a PreDelete hook. Deleting the Application while ManagedWorkloads are left is blocked, with a DeletionError condition. Argo CD retries the hook until they’re gone. To delete it anyway, set guard.uninstall: false in Git and sync first.
  • Earlier Argo CD doesn’t run Helm’s pre-delete hooks, so stop managing the workloads before deleting the Application.

Restoring workloads after the operator is gone

Section titled “Restoring workloads after the operator is gone”

If the operator was removed while ManagedWorkloads were left, nothing restores their workloads. That happens with helm uninstall --no-hooks, kubectl delete -f install.yaml, or deleting an Argo CD Application before Argo CD 3.3. Their napwake.dev/cleanup finalizers, which only the operator removes, also leave the ManagedWorkloads, and the CRD, hanging in Terminating when deleted.

The simplest fix is to reinstall the operator and follow the steps above. Without it:
