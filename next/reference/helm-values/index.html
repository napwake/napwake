What the schema catches

Values are checked against values.schema.json.

A value Caught by
A typo, such as logLevel: warn or defaults.cpuThreshold: 0 The schema. The install or upgrade fails, so the operator never gets it
An unknown one, such as watchNamespace for watchNamespaces, which Helm would ignore The same
What passes through as is, such as resources, affinity, tolerations, nodeSelector, pod annotations and labels Kubernetes only
An unknown timezone The operator, at startup, as the schema can’t list every IANA zone. It exits with invalid --timezone and unknown time zone in its log, and the rollout doesn’t finish

CRD

Section titled “CRD”
Value Default Description
#crds.install true Install the ManagedWorkload CRD and upgrade it with each helm upgrade. Set crds.install: false only if you manage it, such as from config/crd in the repository

Uninstall keeps the CRD

Deleting the CRD would delete every ManagedWorkload. So it’s a chart template with helm.sh/resource-policy: keep, and helm uninstall leaves it. ManagedWorkloads left behind, by an uninstall with --no-hooks or guard.uninstall: false, are still there when Napwake is reinstalled.

For Argo CD, which ignores that, it also carries argocd.argoproj.io/sync-options: Delete=false, so deleting or pruning the Application leaves it too.

Defaults version

Section titled “Defaults version”
Value Default Description
#defaultsVersion the chart’s version, such as 0.2.0-rc.11 Which chart version Helm’s defaults are from. Leave it. See Keeping your settings
What it’s for

helm upgrade --reuse-values to a newer version renders with the old version’s defaults, missing every value added since. Seeing defaultsVersion differ, the chart fills each missing value from its own defaults. They’re in files/defaults.yaml, a copy of values.yaml, which templates can’t read.

Values that are there stay, false, 0 and "" included. With its own defaults it fills nothing, so a default removed with null stays removed.

Operator

Section titled “Operator”
Value Default Description
#replicaCount 1 Operator replicas. More than one needs leaderElection.enabled, or the schema refuses it
#leaderElection.enabled true One replica reconciles, through a Lease. Without it, upgrades stop the old operator before starting the new (strategy: Recreate), so two never act at once
#maxConcurrentReconciles 8 Reconciled at once, so a slow metrics or Prometheus query doesn’t hold up waking another. Sets --max-concurrent-reconciles
#timezone UTC IANA zone, such as Europe/London, for the forecast’s hours and weekdays. Use your users’ zone, so forecasts follow daylight saving. Sets --timezone
#pausing.enabled true false stops every pause this install makes, at once, and wakes what it paused. Requests, activity and autoResume still wake. Sets --pausing=false. See Stop all pausing now
#logLevel info debug, info, error, panic, or a whole number above 0 for more verbose debug levels. Operator and doorman
#logEncoder json json, or console to read by eye. Operator and doorman

Resources

Section titled “Resources”
Value Default Description
#resources.requests.cpu 10m CPU request
#resources.requests.memory 128Mi Memory request
#resources.limits.cpu 500m CPU limit
#resources.limits.memory 512Mi Memory limit. Raise it on clusters with many thousands of workloads
What the operator keeps in memory

Its memory grows with the cluster.

Objects Held
ManagedWorkloads, Deployments, StatefulSets, Services, Ingresses, PVCs, HPAs, Namespaces Cached, only the watched namespaces’ with watchNamespaces
Nodes Cached without image lists
Pods Cached only as spare capacity needs, if bound to a node and not finished, as node, phase and requests. About 2.6 KB each
The EndpointSlices it writes, the doorman Service’s Cached
Other EndpointSlices, ConfigMaps, KEDA ScaledObjects Read when needed, not cached

Go’s garbage collector, in the operator and the doorman, gets a soft limit of 90% of the memory limit. That leaves the rest for memory outside its heap.

It works harder near the limit instead of being OOM-killed. GOMEMLIMIT in the pod overrides it.

Namespaces

Section titled “Namespaces”
Value Default Description
#watchNamespaces [] Namespaces Napwake works in, all if empty. Set, it gets a Role in each, not a ClusterRole, so Kubernetes refuses it anything elsewhere (RBAC). Sets --watch-namespaces, for the doorman too. Each install in a cluster needs its own (more than one install)
#protectedNamespaces [] Patterns, such as prod-*, of namespaces never managed, as if labelled napwake.dev/protected=true, unless labelled napwake.dev/allow-protected=true. kube-*, openshift-*, cattle-*, gke-*, gmp-* and the operator’s and doorman’s namespace always are, with the same exception (protected namespaces). Sets --protected-namespaces

What changes with watchNamespaces.

  • Wake on request still works. The operator always reads the doorman’s EndpointSlices in the release namespace through a <fullname>-doorman-endpoints Role.
  • A dependsOn into an unwatched namespace that allows the dependent’s (napwake.dev/dependents-from) shows as DependencyNotFound=True, reason DependencyNotVisible, and never blocks it.
  • An upgrade or rollback is refused while managed workloads are in a namespace it leaves out. That includes setting watchNamespaces where it was empty. They’d stay paused with no operator (narrowing watchNamespaces).

#defaults.wake request What wakes a paused workload through the doorman. request is any request. ask is only a person’s click on Wake it, for a public URL. Sets --default-wake

Doorman

Section titled “Doorman”

The doorman holds requests to paused workloads and wakes them (Wake on request). It uses the operator’s image, metrics.*, logLevel and logEncoder.

Value Default Description
#doorman.enabled true Deploy the doorman. With false, requests to paused workloads fail
#doorman.replicaCount 2 Replicas, each serving traffic
#doorman.portsPerWorkload 32 Most ports one workload may hold, one per routed Service port, 1 to 10000. So one tenant can’t take all 10,000 the cluster shares. Over it, it isn’t routed (WakeOnRequest=False, reason TooManyPorts). Sets --doorman-ports-per-workload
#doorman.portsPerNamespace 256 Most ports one namespace’s workloads may hold together, 1 to 10000. Sets --doorman-ports-per-namespace
#doorman.healthCheckUserAgents [] Health checkers’ and scrapers’ User-Agent prefixes, whose GET and HEAD don’t wake a workload, such as ["MyCorpMonitor/"]. Or names after (compatible; in a browser-style one. The built-in ones are kube-probe, Prometheus, load balancers’ checks, Blackbox Exporter/, Datadog/Synthetics, Amazon-Route53-Health-Check-Service, GoogleStackdriverMonitoring-UptimeChecks, UptimeRobot, Pingdom.com_bot, NewRelicPinger/, Uptime-Kuma/, Gatus/ and others. See What wakes a workload
#doorman.admissionPolicy.enabled true Two ValidatingAdmissionPolicies. The doorman’s ServiceAccount may change only napwake.dev/last-request, napwake.dev/last-request-from and napwake.dev/turned-away on ManagedWorkloads, though its role may patch them. No one else may set the first two, so a forged last-request-from can’t teach the operator a dependency. See Security
#doorman.podDisruptionBudget.enabled true Keeps one doorman serving through node drains, when replicaCount is above 1
#doorman.nodeSelector {} Empty uses the operator’s
#doorman.tolerations [] Empty uses the operator’s
#doorman.affinity {} Empty uses the operator’s
#doorman.topologySpreadConstraints [] Empty spreads them across nodes and zones where it can
#doorman.podAnnotations {} Empty uses the operator’s
#doorman.podLabels {} Empty uses the operator’s
#doorman.priorityClassName "" Empty uses the operator’s
#doorman.extraEnv [] Extra environment variables. The operator’s extraEnv doesn’t apply
#doorman.resources.requests.cpu 10m CPU request
#doorman.resources.requests.memory 64Mi Memory request
#doorman.resources.limits.cpu 500m CPU limit
#doorman.resources.limits.memory 256Mi Memory limit, enough for some 100,000 pods. Raise it beyond
#doorman.negForwarder.enabled false Optional, for GKE. Routes paused workloads’ Services behind container-native load balancing (NEGs), as a GKE Ingress’s or Gateway’s are. They go through a forwarder Deployment the operator runs in the workload’s namespace while it’s paused. So requests through the load balancer wake them. Grants the operator create and delete on Deployments (RBAC), adds a headless Service <fullname>-doorman-pods, and needs doorman.enabled. See GKE NEGs
#doorman.negForwarder.replicas 2 Pods per forwarder, spread across nodes so one stays while a node drains
#doorman.negForwarder.resources.requests.cpu 10m CPU request, per pod
#doorman.negForwarder.resources.requests.memory 32Mi Memory request, per pod
#doorman.negForwarder.resources.limits.memory 64Mi Memory limit, per pod
The doorman’s memory, shutdown and rollouts
  • It caches ManagedWorkloads and the EndpointSlice controller’s EndpointSlices in watched namespaces, cut to what it reads. That’s about 300 bytes a pod and 700 a Service. Held connections take up to 72Mi more under a flood.
  • On Kubernetes 1.30 and later, it sleeps 5 seconds before shutting down. So kube-proxy and load balancers stop sending new connections first.
  • Rollouts wait 5 seconds after a new pod is Ready (minReadySeconds) before stopping an old one. By then the operator has moved routes to it.

Network policy

Section titled “Network policy”
Value Default Description
#networkPolicy.enabled false NetworkPolicies for the operator and the doorman
#doorman.networkPolicy.ingressFrom [] Peers allowed to reach paused workloads through the doorman, such as your ingress controller’s namespace. Empty leaves the doorman open to every caller. Needs networkPolicy.enabled
#doorman.networkPolicy.egress.enabled false An egress policy letting the doorman connect only to podCIDRs and the API server. Separate from networkPolicy.enabled, and needs a CNI that enforces egress. The doorman needs no DNS, reaching the API server and pods by address
#doorman.networkPolicy.egress.podCIDRs [] Pod CIDRs, in every IP family. Add node CIDRs if a routed workload uses hostNetwork. Required when enabled
#doorman.networkPolicy.egress.apiServer [] The API server’s endpoint CIDRs (kubectl get endpointslices -n default -l kubernetes.io/service-name=kubernetes), not the kubernetes Service’s ClusterIP. Required when enabled
#doorman.networkPolicy.egress.apiServerPorts [443, 6443] Their ports

What the policies admit, with networkPolicy.enabled.

Port Admits
The operator’s and the doorman’s metrics port Only namespaces labelled metrics: enabled
The doorman’s routing ports, TCP 20000-29999 Every source, since every client of a paused workload’s Services is sent there. With ingressFrom and doorman.negForwarder.enabled, the forwarders too, from any namespace. To narrow it, see restricting who can reach the doorman

On Cilium

An ipBlock may not match the API server, which Cilium knows as the kube-apiserver entity, not by address. The egress policy can then cut the doorman off, and its pods fail readiness and log API errors. Leave doorman.networkPolicy.egress.enabled off, and write a CiliumNetworkPolicy allowing egress toEntities: [kube-apiserver] and toCIDR your pod CIDRs.

Guards

Section titled “Guards”

Without the operator, a ManagedWorkload’s finalizer never runs. Its workload stays paused at 0 replicas, its Services routed to the doorman. The guards stop Helm first.

Value Default Description
#guard.uninstall true Refuse helm uninstall while ManagedWorkloads are left, through a pre-delete hook Job, <fullname>-uninstall-guard. Argo CD 3.3 and later runs it as PreDelete, blocking Application deletion too. Earlier versions skip it (uninstall)
#guard.upgrade true Refuse helm upgrade or helm rollback to a watchNamespaces leaving out namespaces with managed workloads. It’s a pre-upgrade and pre-rollback hook Job, <fullname>-upgrade-guard, only with watchNamespaces set. Argo CD runs it as PreSync, before every sync (narrowing)
#guard.nodeSelector {} The hooks’ node selector. Empty uses the operator’s
#guard.tolerations [] Empty uses the operator’s
#guard.affinity {} Empty uses the operator’s
#guard.priorityClassName "" Empty uses the operator’s
#guard.podAnnotations {} Over sidecar.istio.io/inject: "false" and linkerd.io/inject: disabled
#guard.podLabels {} Over sidecar.istio.io/inject: "false". Can’t replace the chart’s labels
#guard.resources 10m/64Mi requests, 100m/128Mi limits The hooks’ resources
How the guards work

Each runs the operator’s image with --guard. It waits two and a half minutes for ManagedWorkloads being deleted. Then it lists those it would leave without an operator, and fails.

Helm stops before changing anything and prints the list.

Guard Counts
Uninstall Every ManagedWorkload in the watched namespaces (all, without watchNamespaces), and any elsewhere with this operator’s napwake.dev/cleanup finalizer. None another install stamped with its namespace in napwake.dev/operator
Upgrade Those the operator took on in namespaces the new watchNamespaces leaves out
  • Each runs as a ServiceAccount of its own name. Its ClusterRole may only list ManagedWorkloads, and the guard reads only their metadata. It’s cluster-wide even with watchNamespaces, since those it looks for may be outside it.
  • The ServiceAccounts and RBAC are hooks too, deleted after the run. A failed Job stays an hour, for kubectl logs.
  • The hooks use image, imagePullSecrets and logLevel.
  • Mesh sidecars are kept out, since a running sidecar would keep the Job from finishing.
  • Their pods carry control-plane: uninstall-guard or control-plane: upgrade-guard, so the operator’s Service and NetworkPolicy don’t select them.
  • --no-hooks skips both.

RBAC

Section titled “RBAC”

What the operator’s ClusterRole, <fullname>-manager, grants by default.

Resource Access For
ManagedWorkloads Manage Including creating them for labelled workloads
Namespaces Read The napwake.dev/managed label and settings annotations
Deployments, StatefulSets Read, scale (scale subresource), patch Patching sets and removes napwake.dev/paused-from while paused. It can’t delete them, and changes nothing else
PersistentVolumeClaims Read Pricing a paused workload’s storage
HorizontalPodAutoscalers, KEDA ScaledObjects Read, and annotate ScaledObjects Pausing a KEDA workload through KEDA
Pod metrics, from metrics-server Read
Pods Read, watch Pricing what pausing frees, sidecars included, and measuring spare node capacity for saved. Cached only if bound to a node and not finished, as node, phase and requests
Nodes Read Pricing at instance types’ list prices, measuring spare capacity. Cached without image lists
Karpenter’s NodePools, Cluster Autoscaler’s cluster-autoscaler-status ConfigMap, Deployments in kube-system List NodePools and Deployments, get the ConfigMap Reporting the node autoscaler (napwake_node_autoscaler). Reads NodePools’ names and consolidation settings, only the rest’s metadata
ConfigMaps Get, one at a time, uncached Learning dependencies from those a workload’s environment references. Can’t list or change them
Events Create User-facing status updates
Services Read
EndpointSlices Manage Routing paused workloads to the doorman

The other roles.

Role Kind, and when Grants
<fullname>-doorman ClusterRole, for the doorman’s own ServiceAccount Read ManagedWorkloads and EndpointSlices. Get the pods a woken workload’s endpoints name, to check each address is its pod’s. Patch ManagedWorkloads to wake them, and create Events. With doorman.admissionPolicy.enabled, patches only set the two request annotations, and the one counting what it turned away
<fullname>-doorman-wake-key Role in the release namespace, for the doorman get and update on one Secret of the same name, which the chart creates empty. The doorman fills it with the key it signs the Wake it button with. It can’t read or list any other
<fullname>-leader-election Role in the release namespace, with leader election Leases (get, create, update) and Events
<fullname>-doorman-endpoints Role in the release namespace, with watchNamespaces Read the doorman’s EndpointSlices
<fullname>-forwarder ClusterRole, or a Role per watched namespace, with doorman.negForwarder.enabled create and delete Deployments for the forwarders. Deletes only its own, owned by a ManagedWorkload. Forwarders run as the namespace’s default ServiceAccount, without its token or API access
<fullname>-view Aggregated into view, edit, admin Namespace viewers may get, list, watch its ManagedWorkloads, as kubectl napwake status and scan do. Kustomize’s managedworkload-viewer-role is aggregated alike
<fullname>-edit Aggregated into edit, admin Namespace editors may create, update, patch, delete its ManagedWorkloads, as pause, wake and enable do. Kustomize’s managedworkload-editor-role is aggregated alike

What changes with watchNamespaces.

  • The operator and the doorman get a Role and RoleBinding in each watched namespace instead.
  • The operator keeps one ClusterRole, to read Namespaces and Nodes and list Karpenter’s NodePools, which only a ClusterRole can grant.
  • Workloads elsewhere can’t be read, scaled or opted in. Dependencies on them aren’t held or woken.
  • With metrics.enabled and metrics.secure, both keep cluster-wide system:auth-delegator bindings, good only for checking scrapers’ tokens.

Everything Napwake reads, writes and sends is in Data and access.
