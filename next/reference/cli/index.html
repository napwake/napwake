Every command

Section titled “Every command”

The request limit and the connection flags every command shares. Namespaces and connections says which namespaces each command reads.
Each request to the API server Gives up after 30 seconds, so a cluster that stops answering ends a command with an error
--request-timeout Changes that limit. Its 0 keeps 30 seconds, where kubectl’s means no limit

Every command takes kubectl’s connection flags:

--kubeconfig, --context, --cluster, --user, --as, --as-group, --as-uid, --token, --server, --certificate-authority, --client-certificate, --client-key, --insecure-skip-tls-verify, --tls-server-name, --proxy-url, --username, --password, --disable-compression and --request-timeout.

The two commands with no section of their own:

Command What it does
version Prints the plugin’s version. It needs no operator
completion Writes a shell completion script, for bash, zsh, fish or PowerShell

scan

Section titled “scan”

Its flags, with their defaults. Scan a cluster shows it in use.

Flag Default What it does
#--namespace -n all you can read Namespace to scan. Repeat for several
#--all-namespaces -A false Every namespace, failing rather than falling back. Not with -n
#--exclude-namespaces kube-system, kube-public, kube-node-lease Namespaces to skip
#--output -o table table, json or yaml
#--limit 25 Rows in the table, idle first, then paused, then active, each by what pausing could free
#--cpu-threshold 10 CPU use above which a workload is active, as a percentage of requests. From 0.1 to 100, such as 10 or 0.5
#--cpu-price 0.031 Your price per vCPU-hour, in dollars, zero or more, for every workload. Unset, each node is priced at its type’s list price, and one with none at AWS on-demand in us-east-1
#--memory-price 0.004 Your price per GiB-hour of memory, in dollars, zero or more, for every workload. Unset, each node is priced at its type’s list price, and one with none at AWS on-demand in us-east-1
#--window 7d Prometheus history to replay, such as 7d or 36h, up to 366d. 0 judges from CPU now
#--idle-after 1h Time without activity that makes a workload idle, as Napwake’s idleAfter
#--prometheus-service the one in the cluster with the most history Prometheus Service in the cluster, as namespace/name or namespace/name:port, read through the API server
#--prometheus-url the one in the cluster with the most history Prometheus API to read, such as Thanos, Mimir, or Google Cloud Managed Service for Prometheus
#--prometheus-selector Label matchers added to every history query, such as 'cluster="prod"', for a Prometheus of several clusters
#--prometheus-header Header for --prometheus-url, as "Name: value", such as "X-Scope-OrgID: tenant" for Mimir. Repeat for several
#--prometheus-bearer-token-file File holding a bearer token for --prometheus-url
#--prometheus-ca-file PEM file of CA certificates to trust for --prometheus-url, besides the system’s
#--prometheus-insecure-skip-verify false Don’t verify --prometheus-url’s certificate
#--timeout 5m How long the scan may take before it gives up
#--html a temporary file Save the web report to this file, to share
#--open true Open the web report, when the table is shown in a terminal

More on the flags

Section titled “More on the flags”

--limit 0 lists every workload. --limit also caps the dependency list, and JSON and YAML list everything.

--cpu-threshold and --idle-after apply now and in the replay. Workloads Napwake manages use their own settings. JSON and YAML give each workload’s as idleAfter.

--prometheus-selector values are double-quoted, as in PromQL.

More on the first line and the columns

Section titled “More on the first line and the columns”

JSON and YAML keep the full context name. Their namespaces counts every namespace read.

Your bill:, under the first line, says what turns what pausing frees into savings. It’s from the node autoscaler nodes finds (JSON nodeAutoscaler).

The node autoscaler Your bill: says
Karpenter, Cluster Autoscaler or EKS Auto Mode It drops only as it removes nodes
Karpenter The same, with how its NodePools consolidate
Cluster Autoscaler, hinted at only by a Deployment The same, and that it may not be running
GKE Autopilot, which bills what pods request It drops as pods stop
None found It won't drop until something removes nodes, with the guide to setting an autoscaler up
Your access doesn’t allow reading what would tell It says so, and names what it couldn’t read

What the columns count, and leave out:

Case What the scan does
COULD FREE/MO Never calls it a saving. Before Napwake runs, the scan can’t know what of it would be saved
Each money and history cell Has the one source the table gives
A live workload Isn’t replayed, as there are no pods for Prometheus to record while it’s paused. Its pauses are what FREED THIS MONTH and SAVED count
A StatefulSet that deletes its PVCs when scaled down Would lose its data to a pause, so Napwake refuses to pause it. It’s left out of what pausing could free and of the next steps
A protected workload Left out of what pausing could free and the next steps
Which are protected Those labelled napwake.dev/protected, and those matching a built-in pattern (kube-*, openshift-*, cattle-*, gke-*, gmp-*). The operator’s own protectedNamespaces patterns show only through a managed workload’s Protected=True
A workload scaled to zero by hand Counted apart in the headline. It counts toward nothing the scan says could be freed

How it decides a workload is idle

Section titled “How it decides a workload is idle”

It uses the signals Napwake uses to pause.

Workload How it’s judged
Managed by Napwake By the activity clock Napwake keeps for it. Idle is no activity until the clock’s pauseAt. That’s idleAfter after the last activity, or longer after pauses made in use
Managed, after pauses made in use BECAUSE says so, such as not idle yet: it woke 6m ago; after pauses made while it was in use, it waits 20 minutes, not 5 minutes
Managed, its activity clock Combines every source configured, Prometheus queries too
Managed, held awake The scan says so, such as for its dependents
Managed, its clock started without activity BECAUSE says what started it
Started by a wake not idle yet: it woke 3m ago
Started as Napwake took it on not idle yet: Napwake began managing it 3m ago
Started by a gap in watching not idle yet: Napwake wasn't watching until 3m ago
Any other, active CPU above --cpu-threshold (10% by default) of what it requests
Any other, active A rollout within --idle-after (1h by default)
Any other, active A napwake.dev/last-activity annotation within --idle-after
Any other, active A napwake.dev/active-until in the future
Any other, idle None of those, with its CPU measured
Unmanaged, without metrics-server As on EKS by default. Judged from its CPU history, and BECAUSE says so
Its state then Where the replay left the activity clock
No CPU requests, or no metrics yet Can’t be judged. It’s in the notes, not the table, and out of the headline’s totals

In the next steps Never suggested, as the tool would revert a label put on by hand too

Infrastructure in JSON and YAML Listed in platform, each with what it is
Left out Found by
Kubernetes’ and platforms’ namespaces, never paused kube-*, openshift-*, cattle-*, gke-* and gmp-*
Napwake’s namespace, never paused Its Deployment’s app.kubernetes.io/name: napwake label
The operator’s and the doorman’s Deployments, never paused control-plane: controller-manager or control-plane: doorman, in any namespace
The same, also needed app.kubernetes.io/name: napwake, or a napwake helm.sh/chart label
What the scan guesses nobody means to pause Well-known kinds, such as ingress controllers, cert-manager, Vault, Argo CD, Flux, service meshes, policy engines and monitoring
The same, by namespace ingress-nginx, cert-manager, vault, argocd, flux-system, istio-system, linkerd, gatekeeper-system, kyverno, monitoring and others
The same, by label app.kubernetes.io/name, app.kubernetes.io/part-of, app, k8s-app or helm.sh/chart
Workloads labelled napwake.dev/ignore=true They aren’t listed at all

What leaving them out changes:

Left out What changes
What Napwake never pauses Apps’ dependencies on it aren’t listed, as Napwake never needs to wake it
The guessed infrastructure Left out of the estimate only. The operator has no such rule
The same, opted in Napwake pauses it like any app, so dependencies on it are listed
No guessing For a workload Napwake manages, or in a namespace labelled napwake.dev/managed=true, such as a preview with its own Vault

History from Prometheus

Section titled “History from Prometheus”

With a Prometheus in the cluster, the scan replays each workload’s last week of CPU and rollouts. It runs Napwake’s activity clock over them, as if managing it with --idle-after and --cpu-threshold.

How it works
Finding it By the Services the Prometheus Operator (so kube-prometheus-stack) and the community Helm chart create
Reaching it Through the API server’s service proxy, so there’s no port-forward or URL to give
Naming it The History: line and the report’s subtitle (JSON history.prometheus)
How much was replayed On the same line and subtitle (JSON history.hours)
Several It reads the one with the most of the window’s CPU history, ranked as below
How many It tries five at most. The History: line lists the others (JSON history.others)
--prometheus-service namespace/name Reads that Service instead, found or not, through the API server
Its port Its API port, or the one you add, as in monitoring/thanos-query:http
--prometheus-url Reads one outside the cluster, such as Thanos or Mimir. See A Prometheus elsewhere
Either, unreadable The scan fails, rather than going on without history
CPU Per container, from cAdvisor’s container_cpu_usage_seconds_total, which every common setup scrapes
Steps Five minutes, coarser for windows over about 34 days
Pods Matched to their workload by name
A Deployment’s pods Those of deleted ReplicaSets too, named <deployment>-<hash>-<suffix>
A long Deployment name If Kubernetes cut its pods’ names short, only current ReplicaSets’ pods are replayed
Sidecars Those added at pod creation are left out of activity, as for the activity clock
An active step A rollout, or the workload’s own CPU above the threshold of its running pods’ requests, as the operator counts it
After --idle-after with none It sleeps until the next active step, which is one wake
CPU within 15 minutes of a pause, or within --idle-after if that’s shorter Shows it was in use
Each such pause in a row Doubles the next wait, up to --idle-after plus an hour, as Napwake does after a pause made in use
A pause that lasts past that window Ends the longer wait
A rollout Wakes it, without counting either way
What it can’t see Requests and activity annotations, which aren’t in Prometheus. It sees only CPU and rollouts
So A workload used with little CPU can look like it would sleep more than it would
Requests and prices Today’s
Rank Preferred
1 cAdvisor’s container CPU from the window’s start, then any CPU, then any that answers
2 A monitoring namespace, in order monitoring, prometheus, observability, kube-prometheus-stack, cattle-monitoring-system, openshift-monitoring
3 A usual name, in order prometheus-operated, kube-prometheus-stack-prometheus, prometheus-server, prometheus, prometheus-k8s
4 The Prometheus Operator’s Service over the community chart’s
5 The first by namespace and name
Time and short history What happens
History’s share The first 60% of --timeout, so a slow Prometheus or Thanos can’t use up the scan
A namespace’s reads Its API reads come before its history query, sharing that time
Once it’s spent A namespace reached after that isn’t queried
A slow query It may take whatever is left, however long. --request-timeout doesn’t cut it short
Not read in time Judged from CPU right now. The notes name these namespaces
The notes’ advice A longer --timeout gives history more time, or --window 0 skips it
A query given up with time left By Prometheus or the API server’s proxy. The notes name the namespaces, and suggest a shorter --window. A longer --timeout wouldn’t help with it
Less history than the window The replay covers what there is, and says how much, such as “Replaying the last 30 minutes”
The same, in the notes A note says it’s shorter than asked
Under a day It can’t show a day’s pattern. The headline says so, in the terminal and the report
The headline’s advice Scan again after a few days
No Prometheus, or no permission to reach it The scan judges from CPU right now, and says why

A Prometheus elsewhere

Section titled “A Prometheus elsewhere”

--prometheus-url reads a Prometheus API your machine can reach, rather than one in the cluster. It needs no cluster permission at all. If it doesn’t answer like a Prometheus API, the scan fails rather than going on without history.

Store or need What to do
A store of several clusters, such as Thanos or Mimir Pass --prometheus-selector with the label that tells them apart
The notes’ hint They suggest it when they see series from more than one source
Authentication --prometheus-header, such as X-Scope-OrgID for a Mimir tenant, or Authorization
Or --prometheus-bearer-token-file. Not both for one header
Its certificate --prometheus-ca-file and --prometheus-insecure-skip-verify
A Prometheus in the cluster These flags don’t apply. It’s reached through the API server, with your kubeconfig
Google Cloud Managed Service for Prometheus GKE’s keeps its data in Cloud Monitoring, so the scan doesn’t find it
Its collectors In gmp-system, with nothing to query. The scan reads another Prometheus if the cluster has one
To read it Give it an access token, and name your project and cluster, as below
Its frontend, deployed in the cluster --prometheus-service NAMESPACE/frontend reads through that, with the frontend’s credentials
Either way The replay’s CPU is there only if it collects cAdvisor’s metrics
Turning those on kubeletScraping in its OperatorConfig
Amazon Managed Service for Prometheus It needs SigV4 signing, which the scan doesn’t do. Point --prometheus-url at a signing proxy

Name the cluster too, since the store holds every cluster in the project.

Section titled “The headline’s counts”
Count What it counts
pausing 14 live workloads Only live workloads Napwake pauses

With none live It says the money came from workloads since put back in dry-run, if there are some

Dependencies

Section titled “Dependencies”

The scan lists the workloads each workload’s environment variables point at, literal or from ConfigMaps.

How it reads them
An address It names a Service in a scanned namespace, in any form cluster DNS gives it
Its forms postgres, postgres.preview-42, postgres.preview-42.svc.cluster.local, or a headless Service’s pod, postgres-0.postgres-hl
Where In a URL, a host:port, or a list of either
The workload The one the Service’s selector picks
Not an address A bare word on its own, such as MODE=postgres
Names Variable names don’t matter. Service names come from the cluster, not a list the scan keeps
Shown Only its scheme, host and port, such as postgres://postgres:5432
Hidden A user, password, path and query string, any of which could hold a credential
In the terminal The variable it was found in. Only JSON and YAML carry the address
Secrets Never read, so addresses there aren’t found. The notes name workloads that take variables from Secrets
Code and files Addresses built in code or read from files aren’t found either

When Napwake manages both, it wakes a dependency with the workload that needs it. It keeps it up while that workload is, so the first request doesn’t wait for it too (Dependencies).

Last column When
woken with it once both are managed Napwake doesn’t manage the workload yet
not managed, so never paused Napwake doesn’t manage the dependency, which stays up anyway
woken and held with it Learned from the workload’s environment, or a wake
declared; woken and held with it Declared with napwake.dev/depends-on
not learned yet Napwake manages it, but hasn’t learned it

Before Napwake manages any workload that needs them, every dependency would say the first. So the scan and the report say it once above the list, and leave the column out.

JSON and YAML

Section titled “JSON and YAML”

The JSON and YAML fields this page names, and what each holds.

Field What it holds
#nodeAutoscaler What would turn freed capacity into savings, the Your bill: line
#wontPause A StatefulSet whose persistentVolumeClaimRetentionPolicy.whenScaled is Delete. BECAUSE says won't pause: PVCs deleted on scale-down
#namespaces Every namespace read. The first line counts only the namespaces listed workloads are in
#history.prometheus The Prometheus read, named on the History: line and the report’s subtitle
#history.hours How much was replayed
#history.others The others found, which the History: line lists
#replicasFromGit The GitOps tool that last set the workload’s replicas
#gitOpsLeavesReplicas Once the tool is told to leave replicas to Napwake
#gitOpsUnchecked Why it couldn’t check
