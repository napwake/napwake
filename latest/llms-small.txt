# Napwake

> Pauses idle Kubernetes workloads in staging, preview and dev, and wakes them on the first request. It never deletes a workload or its data.

Napwake docs # Pause idle Kubernetes workloads in staging, preview and dev. Wake them on the first request. Try it before you install anything. One scan shows what your idle workloads cost. [Scan your cluster](https://docs.napwake.dev/latest/getting-started/scan/)[Install](https://docs.napwake.dev/latest/getting-started/installation/) It never deletes a workload or its data. A request has reached staging while it was asleep. The doorman holds it at the door while staging wakes, then lets it through. Dev stays asleep. Preview is already awake. ## See what’s idle first A team that works 10 hours a day, five days a week, uses staging 50 of 168 hours. The other 70%, it’s idle. `kubectl napwake scan` shows your cluster’s own number before you install anything in it. Install the plugin first, with Homebrew or [another way](https://docs.napwake.dev/latest/getting-started/scan/#1-install-the-plugin). [![The scan report for an example cluster. It leads with 19 of 31 workloads running with no sign of use, then 54% less. Paused when idle, they could cost about $600 a month instead of $1,290. Beside it, the same workloads drawn twice, as they run now and with Napwake pausing the idle ones.](https://docs.napwake.dev/latest/home/scan-report-light.webp)](https://napwake.dev/examples/scan-report/) [![](https://docs.napwake.dev/latest/home/scan-report-dark.webp)](https://napwake.dev/examples/scan-report/) 
```sh
brew install napwake/tap/kubectl-napwake
kubectl napwake scan
```
 * It runs with your kubeconfig and installs nothing in the cluster. * It shows which workloads are idle right now, and what each costs at your nodes' list prices. * With Prometheus, it replays the last week of each workload's CPU and rollouts, and says what pausing would have freed. One file to send your team. It loads nothing from elsewhere and prints to PDF. [Open the example report ↗](https://napwake.dev/examples/scan-report/) [Scan your cluster, step by step](https://docs.napwake.dev/latest/getting-started/scan/) ## Four states, four doors Asleep · paused Scaled to zero. Its Services are routed to the doorman, which wakes it on the first request. Waking up · resuming A request, an activity annotation, or `autoResume` ahead of demand woke it. Its replicas are restored and its dependencies woken. Awake · running Its pods are Ready and held requests passed through. With no activity for `idleAfter`, and no forecast of demand, it pauses again. Needs you · needs attention Something stops Napwake doing its job, and `kubectl napwake status` says what to fix. Its door has a note pinned on it. ## How it works Label a Deployment, StatefulSet or namespace `napwake.dev/managed: "true"` and Napwake creates a ManagedWorkload for it, with its settings from annotations. Then it keeps an activity clock, fed by CPU, deploys, activity annotations and Prometheus. 1. Awake · running Running Activity clock: CPU, deploys, activity annotations, Prometheus 2. No activity for `idleAfter`, and no forecast of demand 3. Asleep · paused Paused Scaled to zero, its Services routed to the doorman 4. A request, an activity annotation, or `autoResume` ahead of demand 5. Waking up · resuming Resuming Replicas restored, dependencies woken Pods Ready, held requests passed through ## What it does * ### Opt in with a label Label a workload or namespace `napwake.dev/managed: "true"`. Settings are annotations in your Git, so Argo CD and Flux work as today. * ### Activity clock Napwake records each workload's last activity: CPU over `cpuThreshold`, a deploy, an activity annotation or a Prometheus query. After `idleAfter` with none, it pauses. No learning period. * ### Demand forecasting A Holt-Winters double seasonal model learns each workload's day and week from up to four weeks of Prometheus. It scores itself from week two and acts when accurate enough: `eager`, `balanced` or `cautious`. It re-learns after drift, never from a holiday. * ### Safe by default Napwake never pauses what it can't measure. A confident forecast can hold a pause off. `dryRun` pauses nothing and shows what would. Anyone else's scale-up is a wake. If a GitOps tool undoes a pause, Napwake tells you how to fix it. * ### Cost tracking Napwake tracks each workload's cost, what pausing frees, and what came off the bill, from each node pool's spare capacity. Freed capacity is money once an autoscaler removes nodes. `kubectl napwake nodes` shows what keeps them. [How to let them go](https://docs.napwake.dev/latest/guides/node-pools/). * ### Metrics and alerts Prometheus metrics for operator health, lifecycle transitions, wakes on request and forecast confidence, with alerting rules. ## Quick example deployment.yaml 
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-api
  namespace: dev
  labels:
    napwake.dev/managed: "true"
  annotations:
    napwake.dev/dry-run: "true"
    napwake.dev/idle-after: "1h"
```
 Napwake watches `my-api` and records each time it’s active. Activity is CPU above `cpuThreshold` (10% of its requests by default), a deploy or an activity annotation. With a [Prometheus query](https://docs.napwake.dev/latest/guides/prometheus-signals/), it’s also the request rate. In dry-run it only measures. Once you run `kubectl napwake enable my-api -n dev`, it pauses the Deployment after an hour with no activity. It wakes it when a request reaches its Service. For every setting, see [Opting in](https://docs.napwake.dev/latest/guides/opt-in/). For settings annotations don’t cover, write a [ManagedWorkload](https://docs.napwake.dev/latest/guides/managed-workload/) yourself. Get started * [Installation →Helm or the Kustomize manifests, with Argo CD or Flux.](https://docs.napwake.dev/latest/getting-started/installation/) * [Quickstart →One workload from idle to paused while idle, woken when used.](https://docs.napwake.dev/latest/getting-started/quickstart/) * [kubectl plugin →`scan`, `status`, `pause`, `wake` and the rest.](https://docs.napwake.dev/latest/getting-started/kubectl-plugin/)

# Installation

> Install Napwake's operator and doorman with the Helm chart, or with the Kustomize manifests that install.yaml is built from.

Before you start * Kubernetes v1.30+, tested in CI on 1.30 and 1.37 * kubectl v1.30+ * [metrics-server](https://github.com/kubernetes-sigs/metrics-server), for pod CPU through the Kubernetes Metrics API. The Quickstart has [the commands to install it](https://docs.napwake.dev/latest/getting-started/quickstart/#metrics-server), with kind’s patch * Helm v3.8+, to install the OCI chart ## Install with Helm Install from the OCI registry, with no `helm repo` to add. Change `Europe/London` to your users’ [time zone](#time-zone). 
```bash
printf '\ntimezone: Europe/London\n' >> napwake-values.yaml
helm install napwake oci://ghcr.io/napwake/charts/napwake --version 0.2.2 \
  --namespace napwake-system --create-namespace -f napwake-values.yaml
```
 Checkpoint 
```bash
# Check the operator and the doorman are running
kubectl get pods -n napwake-system


# Verify the CRD is installed
kubectl get crd managedworkloads.napwake.dev
```
 Within a minute, there’s one `napwake-...` pod, the operator, and two `napwake-doorman-...` pods, all `1/1 Running`: 
```text
NAME                               READY   STATUS    RESTARTS   AGE
napwake-7d9f8c6b5-x2k8p            1/1     Running   0          40s
napwake-doorman-5c8b7d9f6-4qzrt    1/1     Running   0          40s
napwake-doorman-5c8b7d9f6-hm2vw    1/1     Running   0          40s
```
 Check any install this way. Keep the file and upgrade with it. An upgrade given `--set` alone drops your other values ([Keeping your settings](https://docs.napwake.dev/latest/operations/upgrading/#keeping-your-settings)). The chart installs and upgrades the ManagedWorkload CRD. The chart’s version has no `v`. Its image’s tag has one, such as `v0.2.2`. [Helm values](https://docs.napwake.dev/latest/reference/helm-values/) lists every value. ### On EKS Fargate Raise the operator’s, the doorman’s and the guard’s requests to their default limits, in `napwake-values.yaml`: napwake-values.yaml 
```yaml
resources:
  limits:
    cpu: 500m
    memory: 1280Mi
  requests:
    cpu: 500m
    memory: 1280Mi


doorman:
  resources:
    limits:
      cpu: 500m
      memory: 256Mi
    requests:
      cpu: 500m
      memory: 256Mi


guard:
  resources:
    limits:
      cpu: 100m
      memory: 128Mi
    requests:
      cpu: 100m
      memory: 128Mi
```
 EKS Fargate needs every container’s CPU and memory requests to equal its limits ([Fargate Pod configuration](https://docs.aws.amazon.com/eks/latest/userguide/fargate-pod-configuration.html)). That includes the [guard](https://docs.napwake.dev/latest/reference/helm-values/#guards) Jobs that Helm upgrades and uninstalls run. ## With Argo CD or Flux The chart is only in an OCI registry, which Argo CD and Flux name differently. Commit one of these where your GitOps tool syncs from. * Argo CD application.yaml 
  ```yaml
  apiVersion: argoproj.io/v1alpha1
  kind: Application
  metadata:
    name: napwake
    namespace: argocd
  spec:
    project: default
    source:
      repoURL: ghcr.io/napwake/charts
      chart: napwake
      targetRevision: 0.2.2
      helm:
        valuesObject:
          timezone: Europe/London
    destination:
      server: https://kubernetes.default.svc
      namespace: napwake-system
    syncPolicy:
      automated: {}
      syncOptions:
        - CreateNamespace=true
  ```
 * `repoURL` is the registry and path without `oci://`, which tells Argo CD it’s OCI. `chart` is the chart’s name. * The registry is public, so Argo CD needs no credentials. * For the Kustomize manifests, point an Application’s `path` at your kustomization. * Flux napwake.yaml 
  ```yaml
  apiVersion: source.toolkit.fluxcd.io/v1
  kind: OCIRepository
  metadata:
    name: napwake
    namespace: flux-system
  spec:
    interval: 1h
    url: oci://ghcr.io/napwake/charts/napwake
    ref:
      tag: 0.2.2
    layerSelector:
      mediaType: application/vnd.cncf.helm.chart.content.v1.tar+gzip
      operation: copy
  ---
  apiVersion: helm.toolkit.fluxcd.io/v2
  kind: HelmRelease
  metadata:
    name: napwake
    namespace: flux-system
  spec:
    interval: 1h
    chartRef:
      kind: OCIRepository
      name: napwake
    releaseName: napwake
    targetNamespace: napwake-system
    storageNamespace: napwake-system
    install:
      createNamespace: true
    values:
      timezone: Europe/London
  ```
 * It needs Flux 2.6 or later, where `OCIRepository` is `v1`. * `releaseName` keeps the release `napwake`, as these docs call it, instead of Flux’s default, `napwake-system-napwake`. * `storageNamespace` keeps its Helm history beside it, where `helm list -n napwake-system` shows it. * For the Kustomize manifests, point a Flux `Kustomization` at your kustomization. To upgrade, change `targetRevision` or `tag` to the new version. ### Moving a Helm install to Argo CD or Flux Argo CD or Flux can take over a `helm install` where it runs, with the same values. Nothing is reinstalled or restarted, and paused workloads stay paused. Don’t uninstall first. Doing what [`helm uninstall`](#uninstall) asks, stopping managing every workload, wakes every paused one. It also loses each one’s forecast and its tally of what pausing freed. 
```bash
helm get values napwake -n napwake-system
```
 Give the tool these values, and the version in the `CHART` column of `helm list -n napwake-system`. * Argo CD 1. Commit the Application above, with those values in `valuesObject` and that version as `targetRevision`. Argo CD finds every resource as it would make it. It shows `Synced` and `Healthy` without applying anything, so an automated sync doesn’t start. 2. Sync it once by hand, with **Sync** in its UI or with kubectl, giving the Application’s sync options: 
     ```bash
     kubectl patch application napwake -n argocd --type merge -p '{"operation":{"sync":{"syncOptions":["CreateNamespace=true"]}}}'
     ```
 This applies the resources and marks them as the Application’s own, with `argocd.argoproj.io/tracking-id`. It warns that each lacks `kubectl.kubernetes.io/last-applied-configuration`, which Helm doesn’t set and the sync adds. 3. Check it’s `Synced` and `Healthy`: 
     ```bash
     kubectl get application napwake -n argocd
     ```
 4. Delete Helm’s record of the release, its `sh.helm.release.v1.napwake.v<revision>` Secrets, so `helm` no longer acts on it: 
     ```bash
     kubectl delete secrets -n napwake-system -l owner=helm,name=napwake
     ```
 `helm list -n napwake-system` no longer shows it. From now on, change the values or `targetRevision` in Git. * Flux Commit the `OCIRepository` and `HelmRelease` above, with those values in `values` and that version as `tag`. Their `releaseName` and `storageNamespace` are the release’s own. So Flux’s helm-controller finds it in Helm’s storage and takes it over in place. It upgrades it to a new revision, with the same values, and deletes nothing. `helm list -n napwake-system` still shows it, its chart version followed by `+` and the start of the chart’s digest. From now on, change it in Git, since Flux undoes a `helm upgrade` by hand at its next reconcile. ## Install without Helm All three install the CRD, RBAC, the operator (`deployment/napwake-controller-manager`), and the doorman’s Deployment, Service and PodDisruptionBudget, all in `napwake-system`. * install.yaml 
  ```bash
  kubectl apply -f https://github.com/napwake/napwake/releases/download/v0.2.2/install.yaml
  ```
 `install.yaml` is the Kustomize manifests in one file. Set your users’ [time zone](#time-zone) on the operator: 
  ```bash
  kubectl patch deployment napwake-controller-manager -n napwake-system --type=json \
    -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--timezone=Europe/London"}]'
  ```
 Applying an `install.yaml` whose operator arguments changed replaces yours, `--timezone` included. After upgrading, check it’s still there, or use Kustomize, which keeps it. * Kustomize kustomization.yaml 
  ```yaml
  apiVersion: kustomize.config.k8s.io/v1beta1
  kind: Kustomization
  resources:
    - https://github.com/napwake/napwake//config/default?ref=v0.2.2
  patches:
    - target:
        kind: Deployment
        name: napwake-controller-manager
      patch: |-
        - op: add
          path: /spec/template/spec/containers/0/args/-
          value: --timezone=Europe/London
  ```
 
  ```bash
  kubectl apply -k .
  ```
 This uses the manifests as a remote base, pinned to the release, in your own kustomization. It sets your users’ [time zone](#time-zone) on the operator. Set its other [flags](https://docs.napwake.dev/latest/reference/configuration/) the same way. To upgrade, change `ref`. Kustomize fetches bases with git, so `kubectl` or the GitOps tool running it must reach github.com. * From source 
  ```bash
  git clone https://github.com/napwake/napwake.git
  cd napwake
  make docker-build IMG=napwake:dev
  ```
 The image is only in your local Docker. On a [kind](https://kind.sigs.k8s.io/) cluster, load it into the nodes: 
  ```bash
  kind load docker-image napwake:dev --name <cluster>
  make deploy IMG=napwake:dev
  ```
 Elsewhere, push it to a registry the nodes can pull from: 
  ```bash
  make docker-build docker-push IMG=<registry>/napwake:dev
  make deploy IMG=<registry>/napwake:dev
  ```
 `make deploy` installs the Kustomize manifests, `config/default`, with the operator and the doorman running `IMG`. It writes `IMG` into `config/manager/kustomization.yaml`, and `git checkout config/manager` puts it back. ### Prometheus and NetworkPolicies without Helm Two more bases, pinned to the same release, add what these chart values turn on. Add them to your kustomization’s `resources`, or apply one alone: 
```bash
kubectl apply -k "https://github.com/napwake/napwake//config/prometheus?ref=v0.2.2"
```
 From a clone: 
```bash
kubectl apply -k config/prometheus
kubectl apply -k config/network-policy
```
 | Base | Adds | Chart values | | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | | `https://github.com/napwake/napwake//config/prometheus?ref=v0.2.2` | ServiceMonitors for the operator and the doorman, and the [alerting rules](https://docs.napwake.dev/latest/operations/monitoring/#alerting-rules). Needs the Prometheus Operator’s CRDs, and your Prometheus [allowed to read the metrics](https://docs.napwake.dev/latest/operations/monitoring/#scraping) | `metrics.serviceMonitor.enabled`, `metrics.prometheusRule.enabled` | | `https://github.com/napwake/napwake//config/network-policy?ref=v0.2.2` | NetworkPolicies. Only namespaces labelled `metrics: enabled` may scrape the operator and the doorman. The doorman’s routing ports (TCP 20000-29999) stay open to every caller of a paused workload’s Services | `networkPolicy.enabled` | ## Time zone The [forecast](https://docs.napwake.dev/latest/concepts/forecasting/) learns when each workload is busy, by hour of day and day of week. It counts hours in the operator’s time zone. It holds off pausing before busy hours and, with `autoResume`, wakes workloads ahead of them. Set Helm’s `timezone` value, or the operator’s `--timezone` flag, to your users’ IANA zone, such as `Europe/London`, `America/New_York` or `Asia/Kolkata`. The chart’s install notes say which zone the forecast uses. * UTC is the default. A team on daylight saving then finds its workloads woken an hour early or late for half the year. * Teams in different zones can pick the zone most of them work in, or have [an install each](#more-than-one-install). * [Wall-clock alignment](https://docs.napwake.dev/latest/concepts/forecasting/#wall-clock-alignment) has the details. Change the zone later, and what the forecast has learned moves onto the new clock, so it learns your users’ mornings again, as in [Wall-clock alignment](https://docs.napwake.dev/latest/concepts/forecasting/#wall-clock-alignment). To change it on a Helm install, change your values file. If the file has more than one `timezone:` line, Helm uses the last, so keep one. Then upgrade with it at the version you run, as in [Keeping your settings](https://docs.napwake.dev/latest/operations/upgrading/#keeping-your-settings): napwake-values.yaml 
```yaml
timezone: America/New_York
```
 
```bash
helm upgrade napwake oci://ghcr.io/napwake/charts/napwake \
  --version 0.2.2 \
  --namespace napwake-system \
  -f napwake-values.yaml
```
 The operator restarts with it. With Argo CD or Flux, change `valuesObject` or the HelmRelease’s `values` in Git. ## More than one install One install per cluster is usual. Several can share one, such as one per team, if each: * has its own namespace and release name, since the chart names its ClusterRoles and admission policies after the release * sets `watchNamespaces`, with no namespace in two installs’ lists All but one set `crds.install: false`. They share the ManagedWorkload CRD, which belongs to the release that installed it and is upgraded with it. Make that one the newest Napwake. The Kustomize manifests, and so `install.yaml`, are a single install, in `napwake-system`, watching every namespace. Each operator marks the ManagedWorkloads it takes on, and the doorman EndpointSlices it writes, with [`napwake.dev/operator`](https://docs.napwake.dev/latest/reference/labels-annotations/#annotation-napwake-dev-operator), its namespace. Another install leaves those alone, with a `ManagedByAnotherInstall` warning event. So two installs watching one namespace by mistake don’t both pause and wake its workloads. The first to take each one on keeps it. ## Uninstall Stop managing workloads while the operator still runs, so it can scale paused ones back up. 1. Remove the `napwake.dev/managed` label from your workloads and namespaces, in Git if they live there. Napwake deletes the ManagedWorkloads it created from them. Their settings annotations stay, such as `napwake.dev/dry-run`, `idle-after` and `last-activity`. So a workload labelled again is taken on with them. One you’d [enabled](https://docs.napwake.dev/latest/getting-started/kubectl-plugin/#enable-a-workload) is then live from the start, with no dry-run. Remove them from each workload, with any other `napwake.dev/` annotation you set. For a StatefulSet, write `statefulset`: 
   ```bash
   kubectl annotate deployment <name> -n <namespace> napwake.dev/dry-run- napwake.dev/idle-after- napwake.dev/last-activity-
   ```
 Where your workloads live in Git, take the annotations out there, or the next sync puts them back. 2. Delete the ManagedWorkloads you wrote yourself. Each scales its workload back to the replicas it had before the pause. 
   ```bash
   kubectl delete managedworkloads --all --all-namespaces
   ```
 3. Remove the operator: 
   ```bash
   helm uninstall napwake -n napwake-system
   ```
 This keeps the CRD, since deleting it deletes every ManagedWorkload. Once none is left, delete it yourself: 
   ```bash
   kubectl delete crd managedworkloads.napwake.dev
   ```
 Without Helm, delete what you applied: * `kubectl delete -f` with the `install.yaml` URL * `kubectl delete -k .` in your kustomization * `make undeploy` from a clone These delete the CRD too, unguarded, so first check `kubectl get managedworkloads -A` lists none. 4. After `helm uninstall`, delete the namespace. Helm doesn’t delete one that `--create-namespace` made, and it still holds the operator’s leader-election Lease: 
   ```bash
   kubectl delete namespace napwake-system
   ```
 Caution Removing the operator or the CRD first skips step 2’s restore. Paused workloads stay at zero replicas, and their Services still send traffic to the doorman’s deleted pods. [Restore them by hand](#restoring-workloads-after-the-operator-is-gone). ### When `helm uninstall` refuses `helm uninstall` refuses while any ManagedWorkload is left. Its pre-delete hook, the `<fullname>-uninstall-guard` Job, first waits up to two and a half minutes for those being deleted. That lets the operator restore them and drain their doorman ports, which takes up to a minute. Then the hook lists any left and fails, before anything is removed. One deleted moments before you uninstall doesn’t hold it up. | Helm | Error | Above it | | ----------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------ | | 3, before 3.18 (such as 3.16) | `job napwake-uninstall-guard failed` | Nothing | | 3.18 and later | `job napwake-uninstall-guard failed` | The hook’s output | | 4 | `resource Job/napwake-system/napwake-uninstall-guard not ready` | The hook’s output, as one log message with its line breaks escaped | The output names the ManagedWorkloads left after the wait, says what to do and links here. After the first `\n`, it lists each one with the steps above. From Helm 4: 
```text
level=INFO msg="Napwake refuses to uninstall: with no operator, these ManagedWorkloads would be stuck on their finalizers, and their workloads, if paused, would stay at 0 replicas: staging/web. Remove the napwake.dev/managed label from their workloads and namespaces, and delete ManagedWorkloads you created, then uninstall again; see https://docs.napwake.dev/getting-started/installation/#uninstall\n\n..."
```
 When Helm prints only the error, the Job’s log keeps the output for an hour, line breaks and all: 
```bash
kubectl logs job/napwake-uninstall-guard -n napwake-system
```
 No Helm prints it for a revision written by a Helm before 3.18. Such a revision can come from a `helm rollback` after a refused uninstall. A Helm before 3.18 drops the hook’s `helm.sh/hook-output-log-policy` until a newer Helm upgrades the release. ### Restoring workloads after the operator is gone If the operator was removed while ManagedWorkloads were left, nothing restores their workloads. That happens with `helm uninstall --no-hooks`, `kubectl delete -f install.yaml`, or deleting an Argo CD Application before Argo CD 3.3. Their `napwake.dev/cleanup` finalizers, which only the operator removes, also leave the ManagedWorkloads, and the CRD, hanging in `Terminating` when deleted. The simplest fix is to reinstall the operator and follow the steps above. Without it: 1. Scale each paused workload back to the replicas its ManagedWorkload records: 
   ```bash
   kubectl get managedworkloads -A -o jsonpath='{range .items[?(@.status.pause)]}{.metadata.namespace} {.spec.target.kind} {.spec.target.name} {.status.pause.previousReplicas}{"\n"}{end}' |
     while read -r ns kind name replicas; do
       kubectl scale "$kind/$name" -n "$ns" --replicas="$replicas"
     done
   ```
 A workload scaled by KEDA was held at zero through the ScaledObject in its ManagedWorkload’s `status.pause.scaledObject`. Remove that ScaledObject’s `autoscaling.keda.sh/paused-replicas` annotation, or set it back to `status.pause.scaledObjectPausedReplicas` if that’s set. Each paused workload carries the same record in its `napwake.dev/paused-from` annotation, readable once its ManagedWorkload is gone. Remove it once restored: 
   ```bash
   kubectl annotate deployments,statefulsets --all -A napwake.dev/paused-from-
   ```
 2. Delete the EndpointSlices that route paused workloads’ Services to the doorman, so the Services use their own pods again: 
   ```bash
   kubectl delete endpointslices -A -l endpointslice.kubernetes.io/managed-by=doorman.napwake.dev
   ```
 3. Remove the finalizers, so the ManagedWorkloads and the CRD can be deleted: 
   ```bash
   kubectl get managedworkloads -A -o jsonpath='{range .items[*]}{.metadata.namespace} {.metadata.name}{"\n"}{end}' |
     while read -r ns name; do
       kubectl patch managedworkload "$name" -n "$ns" --type=merge -p '{"metadata":{"finalizers":null}}'
     done
   kubectl delete managedworkloads --all --all-namespaces
   kubectl delete crd managedworkloads.napwake.dev
   ```

# kubectl plugin

> Every kubectl napwake command, from scan to enable. What it's for, what it prints, and the flags you'll use most.

## Which command [No operator needed · scan →](#scan-a-cluster) [What’s idle, what it costs, and what pausing could free.](#scan-a-cluster) [Needs Prometheus history · forecast →](#replay-the-forecast) [How the forecast would do on your history, before `autoResume`.](#replay-the-forecast) [Needs the operator · status →](#see-what-napwake-is-doing) [What Napwake is doing with each workload it manages.](#see-what-napwake-is-doing) [No operator needed · nodes →](#see-why-nodes-dont-scale-down) [Why what pausing frees isn’t coming off the bill.](#see-why-nodes-dont-scale-down) [Needs the operator · pause →](#pause-a-workload) [Pause a workload now, such as a preview at the end of the day.](#pause-a-workload) [Needs the operator · wake →](#wake-a-workload) [Wake a workload now, or keep one awake a while, such as for a demo.](#wake-a-workload) [Needs the operator · deps →](#show-a-workloads-dependencies) [What Napwake wakes and holds awake with a workload, and what depends on it.](#show-a-workloads-dependencies) [Needs the operator · enable →](#enable-a-workload) [End dry-run for a workload or namespace, once you trust what Napwake measured.](#enable-a-workload) `scan` and `status` both show idle workloads and money, from opposite ends. `scan` surveys a whole cluster, managed or not, for what could pause and what that could free. `status` shows what Napwake does with what it manages. The rest answer narrower questions. Every flag, JSON field, exit status and permission is in the [kubectl plugin reference](https://docs.napwake.dev/latest/reference/cli/). ## Installation `kubectl napwake version` prints the plugin’s version, and needs no operator. * Homebrew On macOS and Linux: 
  ```bash
  brew install napwake/tap/kubectl-napwake
  kubectl napwake version
  ```
 Homebrew installs the newest release, or the newest release candidate until the first stable release. `brew upgrade` keeps it current. For this version of the docs exactly, use a download. * Krew With [krew](https://krew.sigs.k8s.io/docs/user-guide/setup/install/), kubectl’s plugin manager, installed: 
  ```bash
  kubectl krew install napwake
  kubectl napwake version
  ```
 Krew installs it on Linux and macOS (amd64 and arm64) and Windows (amd64). It installs the newest release [krew-index](https://github.com/kubernetes-sigs/krew-index/blob/master/plugins/napwake.yaml) has, and each release reaches it soon after it’s out. `kubectl krew upgrade` keeps it current. If you installed it from a release’s manifest URL, as these docs said before krew-index listed it, `kubectl krew upgrade` won’t upgrade it. Run `kubectl krew uninstall napwake` once, then install it as above. * Download Download your platform’s archive from the release, and put the binary on your `PATH` as `kubectl-napwake`. On macOS and Linux: 
  ```bash
  os=$(uname -s | tr '[:upper:]' '[:lower:]')
  arch=$(uname -m | sed -e 's/x86_64/amd64/' -e 's/aarch64/arm64/')
  curl -fLO "https://github.com/napwake/napwake/releases/download/v0.2.2/kubectl-napwake-${os}-${arch}.tar.gz"
  tar xzf "kubectl-napwake-${os}-${arch}.tar.gz"
  sudo install "kubectl-napwake-${os}-${arch}" /usr/local/bin/kubectl-napwake
  kubectl napwake version
  ```
 On Windows, download `kubectl-napwake-windows-amd64.tar.gz` from the [release](https://github.com/napwake/napwake/releases/tag/v0.2.2) and extract it with `tar xzf`. Rename `kubectl-napwake-windows-amd64.exe` to `kubectl-napwake.exe`, in a folder on your `PATH`. To check an archive came from the release workflow, see [Verifying a release](https://docs.napwake.dev/latest/reference/security/#verifying-a-release). * Source 
  ```bash
  git clone https://github.com/napwake/napwake.git
  cd napwake
  make build-plugin
  # Binary is at bin/kubectl-napwake
  ```
 ## Namespaces and connections | Commands | Namespaces | | ------------------------------------------------------- | ---------------------------------------------------- | | `scan`, `forecast`, `status` | Every namespace you can read | | The same, if your access doesn’t allow listing them all | Your kubeconfig context’s namespace, with a note | | The same, with `-n` | The namespaces you name | | The same, with `-A` (`--all-namespaces`) | Every one, failing rather than falling back | | `pause`, `wake`, `deps`, `enable` | One namespace, `-n` or your context’s, as in kubectl | Every command also takes kubectl’s connection flags, such as `--context`. See [Every command](https://docs.napwake.dev/latest/reference/cli/#every-command). ## Scan a cluster Find what’s idle, what it costs, and what pausing it could free. Nothing needs installing in the cluster. 
```
kubectl napwake scan

Your bill: drops only as Karpenter removes nodes (it consolidates when underutilized after 1m)
History: the last 7 days, from monitoring/prometheus-operated

  Napwake has 12 workloads paused right now, freeing $1.84 an hour.
  Napwake has freed $96 this month from the 14 live workloads it pauses, and saved $71 of it.
  3 workloads are in dry-run: measured by Napwake since starting, they would have slept 312 hours, freeing $41,
  about $140 a month.
  4 workloads are scaled to zero by hand; Napwake can pause them while idle and wake them on the
  next request instead.
  61 workloads are idle right now, reserving 48.0 vCPU and 190.0 GiB of memory.
  They cost $3,180/month while running, $4.36 an hour: each hour asleep frees that.
  Replaying the last 7 days, Napwake would have paused 58 of 190 unmanaged workloads for 6,120 hours in all,
  and freed $1,240: about $5,380/month.
  Not counted: 4 scaled to zero by hand and 1 without CPU history to replay.

  preview-7    deployment/api         idle (dry-run)       no activity for 5h; measuring since Oct 1                $96       -                  -       41h           4       $40

  ...

Notes:
  - 2 workloads set no CPU requests, so their use can't be measured: kube-tools/agent, ops/exporter
  - 23 infrastructure workloads are left out of the totals and next steps: monitoring (9), argocd (7), ingress-nginx (3) and 4 more in 2 namespaces. Napwake never pauses Kubernetes' own workloads or itself; anything else, infrastructure included, pauses only if you opt it in
```

 `scan` only reads, with your kubeconfig, one cluster at a time. That’s your context, or the one you name with `--context`. Run it before you install Napwake, or after, to see what’s left to opt in. Once Napwake manages a workload, the scan reads its activity clock and shows what Napwake paused and freed. | Line or column | What it says | | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | First line | The cluster, and the workloads listed in how many namespaces | | Its namespace count | Only the namespaces listed workloads are in. 15 namespaces, 12 of them infrastructure, read `14 workloads in 3 namespaces` | | Its cluster name | Shortened for EKS and GKE, such as `staging (EKS us-east-1)` for `arn:aws:eks:us-east-1:123456789012:cluster/staging` | | Other contexts | Shown as named | | `Your bill:` | What turns freed capacity into savings, from the node autoscaler [`nodes`](https://docs.napwake.dev/latest/reference/cli/#nodes-autoscaler) finds ([what it says](https://docs.napwake.dev/latest/reference/cli/#scan-columns-more)) | | `History:` | The Prometheus read, how much was replayed, and others found. See [History from Prometheus](https://docs.napwake.dev/latest/reference/cli/#scan-history) | | STATE | What the workload is doing now, and in brackets how Napwake is involved (below) | | STATE `idle` | No activity for `--idle-after`, or a managed workload’s own wait, so Napwake would pause it now | | BECAUSE | The evidence for the state, then facts such as when it was last deployed, if a week or more ago | | BECAUSE `won't pause: PVCs deleted on scale-down` | A StatefulSet whose `persistentVolumeClaimRetentionPolicy.whenScaled` is `Delete` | | COST/MO | What its requests cost a month while running. See [Prices](https://docs.napwake.dev/latest/reference/cli/#scan-prices) | | COST/HOUR | Without history to replay, what its requests cost an hour while running, to the cent. Each hour paused frees that | | FREED THIS MONTH | Live workloads only. What Napwake freed pausing it since the 1st (`status.cost.freedThisMonth`) | | Its rates | Those Napwake uses for the workload | | SAVED | The part of that which came off the bill as nodes scaled down (`savedThisMonth`) | | COULD SLEEP, in dry-run | The hours Napwake measured it would have slept, since dry-run started. BECAUSE says when | | COULD SLEEP, unmanaged | From the replay. The running hours it would have slept, waiting `--idle-after` after each activity, or longer after a pause made in use | | WAKES | How often activity would have woken it, making whoever caused it wait. Measured in dry-run, replayed otherwise | | COULD FREE/MO | What pausing would free a month, for workloads Napwake doesn’t pause yet. Never called a saving | | COULD FREE/MO, in dry-run | What Napwake measured, the figure BECAUSE gives | | COULD FREE/MO, unmanaged | The replay’s estimate | | Money | Whole dollars, as in `status`. `<$1` is above zero but rounds to nothing. `$0` is none | | `Prices:` | At the end, a summary of what costs were priced at ([Prices](https://docs.napwake.dev/latest/reference/cli/#scan-prices)) | | `Share these numbers:` | The last line, when the report leads with a percentage less. A link to napwake.dev’s page of that card’s numbers, never a name ([The share link](https://docs.napwake.dev/latest/reference/cli/#scan-report)) | | In STATE’s brackets | What it means | | -------------------- | ----------------------------------------------------------------------------------------------------------------------------- | | `unmanaged` | Napwake isn’t involved | | `dry-run` | Napwake measures it, and never pauses it | | `live` | Napwake pauses it while idle | | `protected` | Its namespace is labelled `napwake.dev/protected` or matches a built-in pattern, such as `kube-*`, so Napwake won’t manage it | | `paused (unmanaged)` | Someone scaled it to zero. It costs nothing, but nothing wakes it on a request | Run in a terminal, the scan also writes the report as a web page and opens it in your browser. It’s one self-contained file to email or attach, and it prints cleanly to PDF. See [The web report](https://docs.napwake.dev/latest/reference/cli/#scan-report). 
```bash
# Another cluster in your kubeconfig
kubectl napwake scan --context staging


# Some namespaces, as JSON or YAML, at your own prices
kubectl napwake scan -n preview-42 -n preview-918 -o json --cpu-price 0.045 --memory-price 0.006


# A month of history from a Thanos that holds many clusters, with a 2h idleAfter
kubectl napwake scan --window 30d --idle-after 2h --prometheus-url https://thanos.example.com \
  --prometheus-selector 'cluster="staging"'


# CPU right now only
kubectl napwake scan --window 0


# Save the report to send around
kubectl napwake scan --html workload-scan.html


# The terminal only
kubectl napwake scan --open=false
```

Repeat for several | | `--output` `-o` | `table` | `table`, `json` or `yaml` | | `--window` | `7d` | Prometheus history to replay, such as `7d` or `36h`, up to `366d`. `0` judges from CPU now | | `--cpu-price` | list prices | Your price per vCPU-hour, in dollars, zero or more, for every workload. Unset, each node is priced at its type’s list price, and one with none at AWS on-demand in us-east-1 | | `--memory-price` | list prices | Your price per GiB-hour of memory, in dollars, zero or more, for every workload. Unset, each node is priced at its type’s list price, and one with none at AWS on-demand in us-east-1 | The [`scan` reference](https://docs.napwake.dev/latest/reference/cli/#scan) has every flag, JSON field, exit status and permission. It also says how the scan judges idle, reads history and prices workloads. ## Replay the forecast See how Napwake’s [forecast](https://docs.napwake.dev/latest/concepts/forecasting/) would do on your workloads’ own CPU history, before you trust `autoResume`. It needs Prometheus history, not the operator, and only reads. 
```
kubectl napwake forecast -n preview-42
staging: the forecast replayed over 28 days of CPU history from monitoring/prometheus-operated, times in UTC

NAMESPACE   NAME              FORECAST             READY  COLD  WOKEN FOR NOTHING  WOKEN             WAKES ON
preview-42  api               acts from day one    9/10   1     0                  08:45, 25m ahead  request
preview-42  worker (managed)  acts from Mon 2 Nov  3/10   7     2 (3.5h)           09:45, 20m ahead  query
preview-42  reports           not within 4 weeks   0/6    6     0                  -                 nothing
```
 It runs the operator’s own forecast and decision rules over the history `scan` reads, through the [simulator](https://docs.napwake.dev/latest/concepts/forecasting/#proving-it). | Column | What it says | | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | | FORECAST | When it would act if the workload were opted in today, having [learned all its history](https://docs.napwake.dev/latest/concepts/forecasting/#learning-from-history) | | FORECAST `acts from day one`, or a date | It would act from then | | FORECAST `not within 4 weeks` | A pattern too irregular for the setting | | FORECAST, `(managed)` | A workload Napwake manages shows its own forecast, from `status.prediction` | | `(managed)` `acting`, `learning`, or a date | Its forecast’s state, or when it’s projected to act | | `(managed)` `not within 4 weeks` | It’s earning its confidence, or relearning | | `(managed)` `not learning while paused:` and why | Paused with nothing to see its demand, such as `no Service routes requests to it` | | READY | Mornings it had the workload up before its first use | | COLD | Mornings whose first use found it paused and woke it | | WOKEN FOR NOTHING | Wakes ahead of demand that didn’t come, and how long they kept it up | | WOKEN | When it usually woke it | | WAKES ON | What wakes it once paused (below) | The forecast learns all its history as the operator does for a new workload. [Name a managed workload](#one-workloads-forecast) for its whole forecast, and the fix from `status.prediction.message`. READY to WOKEN replay the history’s last half under `autoResume`, from a forecast that learned only the first half. Having learned less, it’s a little less ready than opting in now would be. A workload counts as used when its CPU is above `--cpu-threshold`, as the activity clock counts it. Use seen only in requests or activity annotations isn’t in Prometheus. | WAKES ON | When | | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `request` | A request through the [doorman](https://docs.napwake.dev/latest/concepts/wake-on-request/) would wake it | | `request`, needs | A Service with a cluster IP that selects its pods on a TCP port | | `request`, also needs | The Service keeps traffic cluster-wide | | `request`, behind GKE NEGs | Only with the doorman’s [forwarder](https://docs.napwake.dev/latest/concepts/wake-on-request/#gke-container-native-load-balancing-negs) on | | `query` | Its ManagedWorkload has a [Prometheus activity query](https://docs.napwake.dev/latest/guides/prometheus-signals/#while-the-workload-is-paused), so only for a managed workload | | `request, query` | Both | | `people` | It [asks before waking](https://docs.napwake.dev/latest/concepts/wake-on-request/#asking-before-waking), and the doorman would route its Services. Only people wake it, and the forecast learns its paused hours from whether they did | | `people`, not routed | One the doorman wouldn’t route is `nothing` or `query` | | `people, query` | The same, with a query too | | `nothing` | People wake it by hand, and the forecast doesn’t learn the hours it’s paused | | Flag | Default | What it does | | ------------------ | ---------------- | -------------------------------------------------------------------------------------------------------------------------- | | `--namespace` `-n` | all you can read | Namespace to replay. Repeat for several | | `--window` | `28d` | History to read, from `2d` to `34d`. The operator learns up to four weeks | | `--forecast` | `balanced` | How soon the forecast acts for unmanaged workloads. See [Forecast setting](https://docs.napwake.dev/latest/concepts/forecasting/#forecast-setting) | | `--timezone` | the operator’s | The zone whose hours and weekdays the forecast learns, and times show in | | `--output` `-o` | `table` | `table`, `json` or `yaml`. JSON and YAML give every workload’s days | The [`forecast` reference](https://docs.napwake.dev/latest/reference/cli/#forecast) has every flag and JSON field, how it reads history, and what would wake a workload. ### One workload’s forecast Name a workload, as `api` or `statefulset/postgres`, to see its forecast.  For a managed workload it first shows Napwake’s own forecast. That’s from `status.prediction` and the state saved there, as the operator restores it. Then, for any workload, the replay. | Line | What it says | | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | | First line | `acting`, `learning`, `relearning` or `not learning`, as in `status`’s FORECAST | | Under it | The operator’s `status.prediction.message`, what it waits for and why | | Phase | Each season’s phase, daily and weekly, `Observing`, `Suggesting` or `Active`. See [Phase lifecycle](https://docs.napwake.dev/latest/concepts/forecasting/#phase-lifecycle) | | Hours seen | Hours of the day seen since it started or last relearned, and hours of the week | | To act | It needs all 24 hours of the day | | Learned | Hours of demand learned | | Learned, from history | How many came from Prometheus history when Napwake began managing it (`status.prediction.history`) | | Learned, live | How many it learned since, out of how long it’s been managed | | History | With no history learned, the operator’s reason | | Confidence | How right the last day’s and last week’s forecasts were, and the confidence it acts from | | Acts from `now` | It’s acting | | Acts from a time | When it’s expected to start (`status.prediction.startsActing`), if the coming days repeat the last week | | Acts from `not known until it has seen every hour of the day` | While it’s still observing | | Acts from `not known until it has scored a day of its forecasts` | While it’s still observing | | Acts from `not expected within 4 weeks` | A pattern too irregular for its setting | | Busy hours | Hours of the next 24 it expects demand in, at or above `cpuThreshold` | | Busy hours, peak | The most it expects, as a share of the CPU requested | | Busy hours, effect | It holds off a pause before each. For a ManagedWorkload written by hand, which annotations don’t change, set `spec.idlePolicy.autoResume: true`.  In a terminal, the states are in colour, each beside a door, so they read without the colour too: | STATE | Colour | Door | | ---------- | ------ | ---- | | `paused` | Blue | Shut | | `running` | Green | Open | | `resuming` | Yellow | Ajar | What needs attention is red, and the table’s header and dry-run grey. kubectl napwake enable my-api -n dev
 It sets `napwake.dev/dry-run` to `"false"`. After `idle-after` with no activity, which NEXT counts down, Napwake scales `my-api` to zero and remembers its 2 replicas. CheckpointAsleep 
```bash
kubectl get deployment my-api -n dev
# READY: 0/0
```
 ## 6. Wake it with a request Wait 5 minutes after READY reads `0/0`. A request or a wake sooner makes it a [wrong pause](https://docs.napwake.dev/latest/concepts/idle-detection/#paused-while-in-use). Napwake would then warn `PausedWhileInUse`, and wait 10 minutes before pausing again. Start a pod to send the request from, and wait until it runs: 
```bash
kubectl run curl -n dev --image=curlimages/curl:8.7.1 --restart=Never --command -- sleep 600
kubectl wait pod/curl -n dev --for=condition=Ready --timeout=2m
```
 Send the request, timed: 
```bash
kubectl exec -n dev curl -- curl -s -o /dev/null -w '%{http_code} after %{time_total}s\n' http://my-api
```
 
```text
200 after 1.084523s
```
 The [doorman](https://docs.napwake.dev/latest/concepts/wake-on-request/) holds the request and wakes `my-api`. The request waits a second or two, while `my-api`’s pods start and pass their readiness probe. A browser coming through an Ingress or a Gateway gets a waking-up page, which loads the app once it’s up. Then remove the pod: 
```bash
kubectl delete pod curl -n dev --now
```
 `kubectl port-forward` goes straight to a pod, so it can’t reach a paused workload. Wake it first: 
```bash
kubectl napwake wake my-api -n dev
```
 CheckpointAwake curl printed `200 after` a second or two, once `my-api` was Ready. ## 7. Stop managing it 
```bash
kubectl label deployment my-api -n dev napwake.dev/managed-
```
 `my-api` keeps the settings annotations `napwake.dev/dry-run`, now `"false"`, `idle-after` and `last-activity`. Labelled again, it’s taken on with them, so it’s live from the start, with no dry-run. To start again from step 3, remove them: 
```bash
kubectl annotate deployment my-api -n dev napwake.dev/dry-run- napwake.dev/idle-after- napwake.dev/last-activity-
```
 CheckpointAwake · not managed Within a minute, as the doorman’s port drains, `my-api`’s ManagedWorkload is gone. Had it been paused, it would be scaled back to its replicas at once, never left switched off. # Architecture

> Napwake runs in your cluster as one binary, in two Deployments. One is the operator, the other the doorman.

```mermaid
flowchart TB
    subgraph operator["Operator Deployment"]
        optin["Opt-in reconcilers<br/>Deployments, StatefulSets"]
        mwr["ManagedWorkload reconciler<br/>activity clock, pause and resume,<br/>dependencies, cost"]
        forecast["Forecast engine<br/>one per workload"]
        optin --> mwr
        mwr --- forecast
    end
    subgraph doorman["Doorman Deployment"]
        door["Holds requests to paused workloads,<br/>wakes them, passes requests through"]
    end
    clients["Clients, ingress controllers,<br/>load balancers"] -- "Service of a paused workload" --> door
    door -- "napwake.dev/last-request" --> api
    mwr --> api["Kubernetes API server"]
    mwr --> ms["metrics-server"]
    mwr -.-> prom["Prometheus<br/>optional"]
```
 Napwake is a Kubernetes operator built on [controller-runtime](https://github.com/kubernetes-sigs/controller-runtime). The [doorman](https://docs.napwake.dev/latest/concepts/wake-on-request/) wakes paused workloads on request. ## Reconcilers The operator runs two kinds of reconciliation loop. ### ManagedWorkload reconciler The main one. It watches `ManagedWorkload` CRs and drives each workload through its [lifecycle](https://docs.napwake.dev/latest/concepts/lifecycle/). * A reconcile times out after 2 minutes. * `--max-concurrent-reconciles` workloads are reconciled at once, 8 by default. One slow metrics or Prometheus query doesn’t hold up another workload’s wake. * Each workload’s forecast engine runs in memory. It’s saved to `status.prediction.state` each hour it learns, so it survives operator restarts and leader changes. * Reconciles wait in one queue, so a wake isn’t queued behind every workload’s checks: | Order | Reconciles | | ---------- | --------------------------------------------------------------------------------------------------------- | | First | What wakes a workload. A request the doorman holds, an activity or pause annotation, a scale-up from zero | | Also first | A resume under way | | Then | Other changes | | Last | Periodic checks of awake and paused workloads, with their metrics and Prometheus queries | ### Opt-in reconcilers One for Deployments, one for StatefulSets. Each watches its workloads, their namespaces, and the ManagedWorkloads created from them. It turns the `napwake.dev/managed: "true"` label into a ManagedWorkload, as [Opting in](https://docs.napwake.dev/latest/guides/opt-in/) describes. ## Internal packages | Package | Does | | --------------------- | --------------------------------------------------------------------------------------------------- | | `internal/controller` | The reconcilers | | `internal/forecast` | Holt-Winters model, phase lifecycle, confidence scoring, anomaly detection | | `internal/signal` | Prometheus activity queries | | `internal/autoscaler` | Finds HPAs and KEDA ScaledObjects. Holds a KEDA one at zero while paused | | `internal/gitops` | Tells from field managers whether a GitOps tool sets the replicas, and how to tell it to leave them | | `internal/lifecycle` | Pause and resume, through the scale subresource | | `internal/discovery` | `kubectl napwake scan` | | `internal/doorman` | The doorman | | `internal/cost` | Rates, node list prices, monthly projection | | `internal/metrics` | Metric definitions, and the Kubernetes Metrics API reader | ## External dependencies | System | Napwake uses it to | | --------------------------------------------------- | ----------------------------------------------------------------------- | | Kubernetes API server | Scale workloads, and route Services’ EndpointSlices to the doorman | | Kubernetes API server, for pricing and dependencies | Read pods, PVCs, nodes’ labels, ConfigMaps, HPAs and KEDA ScaledObjects | | metrics-server, required | Read pod CPU | | Prometheus, optional | Run PromQL activity queries | ## Freed and saved Napwake works at the workload layer, and doesn’t manage nodes. What a pause or scale-down frees comes off the bill once a node autoscaler removes nodes. Every 5 minutes, the leader measures what’s [saved](https://docs.napwake.dev/latest/concepts/cost-tracking/#how-saved-is-measured), from cached nodes and pods. Every 10 minutes, it exports which node autoscaler runs as `napwake_node_autoscaler`. ## Leader election For high availability, run several operator replicas with `--leader-elect`, controller-runtime’s leader election. Only the leader reconciles, and a standby takes over if it fails. Every doorman replica serves traffic, with no leader. ## Security model * The operator runs as non-root, in a distroless container. * RBAC is scoped to the minimum. See [Data and access](https://docs.napwake.dev/latest/reference/data-and-access/#rbac). * Metrics are served over HTTPS, with authentication, by default. * HTTP/2 is off by default, to mitigate known vulnerabilities. Next * [Lifecycle →The phases a workload moves through.](https://docs.napwake.dev/latest/concepts/lifecycle/) * [Cluster Autoscaler →Turning what a pause frees into savings.](https://docs.napwake.dev/latest/guides/cluster-autoscaler/)

# Cost tracking

> What pausing a workload frees, and how much of that comes off your bill.

CPU 1 vCPU3 vCPU 4 vCPU paused, 1 vCPU spare. **3 vCPU short: saved** Memory 12 GiB 12 GiB paused, 14 GiB spare. **None short: nothing saved** **Fits in spare capacity: freed**Wouldn't fit: freed, and saved The [worked example](#worked-example)'s node pool. Pausing freed all of it. Only what the pool couldn't take back, 3 vCPU, came off the bill. Napwake tracks what each workload costs, frees and saves, in its ManagedWorkload’s `status.cost`. Tracking is always on. The figures cover the current calendar month in UTC. Each month starts from zero, and last month’s figures aren’t kept. ## Freed and saved Freed becomes saved only once nodes go. The two numbers answer different questions: | | Field | What it is | | ----- | ---------------- | ---------------------------------------------------------------------------------------------------------------- | | Freed | `freedThisMonth` | What the paused replicas requested, at their nodes’ list price, while paused. What pausing released on its nodes | | Saved | `savedThisMonth` | The part of that which provably came off your bill | Napwake works at the workload layer, and your bill is for nodes. Pausing removes pods, which frees what they requested. That’s money only once a node autoscaler removes nodes, such as Cluster Autoscaler, Karpenter or a managed equivalent. With none, or with scale-down blocked, a pause saves nothing, and `savedThisMonth` says so. ### How saved is measured Saved is what the pauses hold off the bill right now. Every 5 minutes, the operator’s leader measures it in each node pool. It asks how much of what’s paused there the pool’s nodes could hold if it came back: | | In CPU and in memory | | --------- | --------------------------------------------------------------------------------------------------------------------------------------------- | | Paused | What the replicas Napwake holds paused in the pool requested | | Spare | What the pool’s schedulable, Ready nodes have left, allocatable less what their bound pods request, finished pods aside | | Shortfall | `max(0, paused − spare)`. Bringing the paused replicas back would need that much more capacity, so it costs at least that | | Credited | The shortfall, shared by the pool’s paused workloads in proportion to what each holds paused there, as `savedCPUHours` and `savedMemoryHours` | | Priced | `savedThisMonth` is those hours at the workload’s rates, as for freed, `costTracking.rates` included | | Recorded | A pause records its pools, and its pods in each, in `status.pause.resources.nodePools` | Saved is a **lower bound**. CPU and memory are compared apart. Spare is summed across the pool’s nodes, as if pods could be split between them. Real scheduling only ever needs more. So saved never credits capacity that’s still there, and can undercount but never overcount. Nodes removed for any reason count, if the paused replicas would need them back. That’s by an autoscaler after a pause, by consolidation, or by hand. If other workloads scale down, the paused replicas fit in what they leave, so the credit falls. #### Worked example | | In the example | | --------------------------------- | -------------------------------------------------------------------------------------------------- | | Pool | Three `m6i.xlarge` nodes in us-east-1, 4 vCPU and 16 GiB each. Its pods request 11 vCPU and 34 GiB | | Paused | `api`, 4 replicas of 500m and 1 GiB, and `worker`, 2 replicas of 1 vCPU and 4 GiB | | Paused in all | 4 vCPU and 12 GiB | | Spare | 1 vCPU and 14 GiB | | Shortfall | 3 vCPU. No memory, which would fit, so memory saves nothing | | Credited | 1.5 vCPU each to `api` and `worker`, which hold 2 vCPU each | | Credited every 5 minutes | 0.125 vCPU-hours each | | $/hour | At an `m6i.xlarge`’s $0.0317 per vCPU-hour, `api` frees $0.080 (2 vCPU and 4 GiB) and saves $0.048 | | A node removed | Spare falls, and saved rises towards freed | | Another team takes the spare vCPU | Saved rises too, as the paused replicas couldn’t come back without a node | ## How costs are calculated Everything is priced on what the pods **request**, not what they use. Requests are what a pod reserves on a node. So they’re its cost in capacity, and what a pause frees. Sidecars injected when the pods were created count too, such as a service mesh proxy. The template doesn’t list them, but pausing frees them. ### Resource hours The month’s totals are resource-hours, updated at every phase change and at least every 5 minutes. So time counts in the phase it was spent in. | Field | Counts | | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | | `awakeCPUHours`, `awakeMemoryHours` | vCPU-hours and GiB-hours the replicas requested while awake, in any phase but `Paused` | | `storageHours` | GiB-hours of the PersistentVolumeClaims its pods mount, in every phase. A pause doesn’t free storage | | `pausedCPUHours`, `pausedMemoryHours` | vCPU-hours and GiB-hours the replicas Napwake paused had requested, while paused. What pausing freed | | `savedCPUHours`, `savedMemoryHours` | Its share of the vCPU-hours and GiB-hours its pools were [short](#how-saved-is-measured) of. What pausing saved, at most the paused hours | ### Prices Resource-hours become dollars at a rate per vCPU-hour, per GiB-hour of memory, and per GiB-month of storage. Each comes from the first of these that sets it: 1. 1Your own ratesIn `spec.costTracking.rates` 2. 2Its nodes' list priceIn `status.cost.listRates`. CPU and memory only 3. 3The defaultsFor nodes with no list price, such as on-premises, custom, or kind nodes | List price | | | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | | Instance type and region | From each pod’s node’s labels, `node.kubernetes.io/instance-type` and `topology.kubernetes.io/region` | | Which price | On-demand, or spot for a [spot node](#spot-nodes), averaged over the workload’s pods | | `status.cost.listPrice` | Which it was. `OnDemand`, `Spot`, or `SpotAndOnDemand` for pods on both | | When | Read again hourly while the workload is awake, and kept while it’s paused | | A pause | What it frees and saves is priced at the nodes it last ran on | | Left out | Savings plans, reserved instances, committed-use discounts, negotiated rates, and AWS spot’s hour-by-hour price. Set `costTracking.rates` for those | | Resource | Default rate | Source | | -------- | --------------------------------------------- | --------------------------------------------------------------------------------------- | | CPU | $0.031/vCPU-hour | AWS on-demand, an `m6i.large` in us-east-1, 2026. So changing `costTracking.rates` reprices the month so far, not only what follows. #### Spot nodes A node labelled as spot or preemptible is priced at its type’s spot price in its region. | Label | On | | ------------------------------------------------------------------------------- | ----------------------- | | `karpenter.sh/capacity-type: spot` | Karpenter, on any cloud | | `eks.amazonaws.com/capacityType: SPOT` | EKS managed node groups | | `cloud.google.com/gke-spot: "true"`, `cloud.google.com/gke-preemptible: "true"` | GKE | | `kubernetes.azure.com/scalesetpriority: spot` | AKS | | Spot price | | | ---------------------------------------- | -------------------------------------------------------------------------------------------------------- | | Google Cloud, Azure | One published price per region | | AWS | Moves with demand. Napwake uses the average across the region’s zones when its price table was generated | | So for AWS | Close, but not what any one hour cost | | A type its provider doesn’t sell as spot | On-demand. `kubectl napwake scan` says which workloads that leaves costing less than shown | ### Custom rates Set your own rates to match what you pay. These are example rates: managedworkload.yaml

# Dependencies

> Keep a database awake while the apps that use it are, and wake it with them.

A request wakes api, and the doorman holds it. Napwake wakes api's dependencies, postgres and cache, at the same time. Databases, message brokers, caches and workers never see outside traffic. So their [activity clock](https://docs.napwake.dev/latest/concepts/idle-detection/) can run out while the workloads using them are busy. Napwake [learns](#learned-dependencies) who needs what from each workload’s environment, or you declare it with `dependsOn`: managedworkload.yaml 
```yaml
apiVersion: napwake.dev/v1alpha1
kind: ManagedWorkload
metadata:
  name: api
  namespace: preview-42
spec:
  target: {kind: Deployment, name: api}
  dependsOn:
    - {kind: StatefulSet, name: postgres}                         # same namespace
    - {namespace: messaging, kind: StatefulSet, name: nats}       # another namespace
  idlePolicy:
    idleAfter: 1h
  prediction: {}                                                  # the default, balanced
```
 | `dependsOn` | | | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Goes on | The workload that **needs** the other | | Names | The dependency’s Deployment or StatefulSet, not its ManagedWorkload | | `namespace` | Defaults to the ManagedWorkload’s own | | As an annotation | `napwake.dev/depends-on: "statefulset/postgres, messaging/statefulset/nats"` on the workload or its namespace. See [Opting in](https://docs.napwake.dev/latest/guides/opt-in/#settings) | ## The rules | Rule | | | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | A dependency doesn’t pause while anything that depends on it is awake | Its own clock keeps running meanwhile | | The last dependent pauses | The dependency pauses on its next check, if its own clock has run out | | A dependent that’s waking holds it too | Paused, with a wake already asked for: a request the doorman holds for it, an [activity annotation](https://docs.napwake.dev/latest/concepts/idle-detection/#activity-annotations) on its ManagedWorkload or its workload, or a wake request, set since its pause. So the dependency doesn’t start to pause as the dependent wakes | | The dependents are read again before it pauses | From the API server, which can have a wake, or a dependency just learned, that the operator’s cache hasn’t seen yet. Not in dry-run, where nothing pauses. Once more just before it’s scaled to zero, after the doorman’s takeover. A dependent awake then, such as one that learned it depends on it since, calls the pause off (`PauseCancelled`) | | Waking a workload wakes its dependencies | Before it resumes, Napwake sets `napwake.dev/last-activity` on each dependency’s ManagedWorkload, the usual [activity annotation](https://docs.napwake.dev/latest/concepts/idle-detection/#activity-annotations) wake. A `WokenByDependent` event on the dependency names the dependent | | Seeing it | `kubectl describe` shows it | | It chains | If Postgres depends on something, that wakes too | | Everything wakes at once | By default, so a chain doesn’t add up to cold starts in a row | | Waking a dependency never holds up its dependent | The dependent wakes, or is handed back or deleted, regardless | | A dependency can’t be woken | As when a policy engine won’t let Napwake annotate its ManagedWorkload. The dependent gets a `DependencyWakeFailed` warning event | | A dependency’s [forecast](https://docs.napwake.dev/latest/concepts/forecasting/#what-an-hour-records) learns its dependents’ use | An hour a dependent holding it is in use is an hour the dependency is in use, whatever its own CPU. A dependent’s wake, which stamps it, isn’t. So woken ahead by the forecast or by the morning’s first request, a dependency learns the same hours | A dependency held awake says why: 

 ## Waiting for a dependency to be ready `waitForReady` keeps the dependent from starting until the dependency serves. Set it for an app that fails if it starts first. An example is an API that gives up after a few retries while its database replays its write-ahead log: 
```yaml
dependsOn:
  - {kind: StatefulSet, name: postgres, waitForReady: true}
  - {kind: Deployment, name: cache}          # wakes at the same time
```
 The dependent stays in `Resuming`, not scaled up: 
```text
WaitingForDependencies=True   waiting for preview-42/statefulset/postgres (0 ready)
```

 ### What it saves and costs The pause comes once the hour people leave in is over, since that hour is learned as busy. On office hours ending at 17:30, it comes at 18:00. The activity clock would have paused at 18:29, an `idleAfter` after the last busy minute. The longer `idleAfter`, the more that saves. Anyone who comes in an hour forecast quiet, before `idleAfter` would have run out, pays a cold start. The simulator measures both at `balanced`, for a workload at 40% of its CPU request in use. It counts the weeks after the forecast acts. A component’s smoothing parameter sets the size of its step. | Component | What it represents | Smoothing parameter | | ----------------- | --------------------------------------------------------------------------- | ------------------- | | Level | The mean demand | α=0.01 | | Trend | Whether demand is growing or shrinking | β=0.001 | | Daily components | 24 offsets, one per hour of day, the shape of an average day | γ1​=0.1 | | Weekly components | 168 offsets, one per hour of week, how each weekday departs from that shape | γ2​=0.5 | Each hour, the model compares the hour’s utilisation Y(t) with what it predicted, for confidence scoring. Then it updates all four by exponential smoothing. It’s additive, since idle workloads spend much of their time at zero demand. A multiplicative model, which divides by the level and the seasonal factors, diverges there. The forecast h hours ahead adds the level, h hours of trend, and that hour’s daily and weekly offsets. That’s the total absolute error of the hourly forecasts over a window, divided by the total demand in it. Napwake detects these regime changes with z-score anomaly detection. An hour is an anomaly when its error is more than three standard deviations from the recent errors. 1. Each hour, the signed prediction error e(t)=Y(t)−F(t) becomes a two-sided z-score. It uses an exponentially weighted mean μ and standard deviation σ of recent errors, which remember about a week. A sudden surge and a sudden disappearance both count. z(t)=max(σ,f)∣e(t)−μ∣​ 2. If z(t)>3.0, the hour is an anomaly. The model learns from it only up to 3 standard deviations, so a single spike isn’t learned as a pattern. But if the last error in its hour of the week was as far out, the same way, it isn’t an anomaly. It’s a weekly pattern, such as a Tuesday night batch job, and it’s learned in full. 3. 3 or more anomalies within 24 observed hours are a regime change. | After | The forecast does this | | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | An anomaly, or any hour in the day after a regime change | It holds the change to that hour of the week until the same hour the next day. # Idle detection

> When Napwake pauses a workload, and what wakes it again.

The clockidleAfter: 1h The clock: awake from 08:00 to 10:14, asleep from 10:14 to 12:00. Asleep Waking up Awake**09:14 last activity**10:14 pauseAt The [status example](#restarts-and-outages). The last activity was at 09:14. With the default `idleAfter` of an hour, it pauses at 10:14. Napwake keeps an **activity clock** for every ManagedWorkload. It’s the last time anything showed the workload was in use. Any sign of activity resets it. Once the clock is older than `idlePolicy.idleAfter`, Napwake pauses the workload. It’s scaled to zero, keeping its replica count and a resource snapshot. * There’s no learning period. A new workload can pause after its first `idleAfter` without activity. * With `idlePolicy.pauseEarly`, a confident forecast can pause it sooner ([Pausing early](https://docs.napwake.dev/latest/concepts/forecasting/#pausing-early)). managedworkload.yaml 
```yaml
spec:
  idlePolicy:
    idleAfter: 1h        # default
    activity:
      cpuThreshold: 10   # percent of CPU requests, 0.1 to 100, the default
```
 Write a threshold that isn’t a whole number as a string, such as `cpuThreshold: "0.5"`. Kubernetes APIs write decimals that way. It suits a workload that idles at a fraction of a percent. ## What counts as activity Every source is checked. The most recent wins, and none has priority. | Source | Counts when | Setup | | --------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | | CPU | Above `activity.cpuThreshold`% of what the reporting pods request, from 0.1 to 100 | metrics-server | | Deploy | The pod template changes, such as an image, an environment variable, any edit | None | | `napwake.dev/last-activity` | It holds a time newer than the last activity | Your tooling | | `napwake.dev/active-until` | It holds a time in the future. A hold, not an activity time | Your tooling | | `napwake.dev/last-request` | It holds a time newer than the last activity | The [doorman](https://docs.napwake.dev/latest/concepts/wake-on-request/), when it holds a request for the paused workload | | Prometheus | A query in `activity.prometheus` returns above zero | `--prometheus-url` ([Prometheus activity](https://docs.napwake.dev/latest/guides/prometheus-signals/)) | * A change to the replica count isn’t a deploy, so Napwake’s own pause and resume never look like activity. * Memory isn’t a source. It stays allocated whether the workload is used or not. ### Activity annotations Set either on the ManagedWorkload or its target, as an RFC 3339 time. 
```bash
# Record activity now, e.g. from a developer portal when someone opens an environment
kubectl annotate deployment my-api -n staging --overwrite \
  napwake.dev/last-activity="$(date -u +%Y-%m-%dT%H:%M:%SZ)"


# Keep the workload awake until 18:00 UTC today, such as during a demo. Run it before then, since a time already past does nothing
kubectl annotate deployment my-api -n staging --overwrite \
  napwake.dev/active-until="$(date -u +%Y-%m-%dT18:00:00Z)"
```
 [`kubectl napwake wake`](https://docs.napwake.dev/latest/getting-started/kubectl-plugin/#wake-a-workload) wakes it through [`napwake.dev/wake-requested`](https://docs.napwake.dev/latest/guides/pause/#wake-now) instead, and waits until it’s Running. * A `last-activity` time in the future counts as now. For a hold, use `active-until`, which says when it ends. * Annotations only keep a workload awake or wake it. They never pause it. * A value that isn’t RFC 3339, such as epoch seconds or a space for the `T`, is ignored everywhere. Each gets one `InvalidActivityAnnotation` warning event on the ManagedWorkload, naming the annotation and where it is. ## The decision Each check runs these steps in order. The first that holds decides. | Step | If | Then | | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | | 1 | CPU or a configured query [can’t be read](#when-a-source-cant-be-read) | Stay awake | | 2 | `active-until` is in the future | Stay awake | | 3 | The last activity was under `idleAfter` ago, or longer after [a pause made in use](#paused-while-in-use) | Stay awake, unless the forecast pauses it early (below) | | 4 | The [forecast](https://docs.napwake.dev/latest/concepts/forecasting/) is confident (`DailyActive` or later, `dailyPhase: Active`) and predicts above `cpuThreshold` in this hour or the next | Stay awake, with `IdleVetoed` | | 5 | A workload awake, or [waking](https://docs.napwake.dev/latest/concepts/dependencies/#the-rules), [depends on](https://docs.napwake.dev/latest/concepts/dependencies/) this one, or `dependsOn` forms a cycle | Stay awake, with `HeldByDependents` or `DependencyCycle` | | 6 | None of these | `Idle`, then [paused](https://docs.napwake.dev/latest/guides/pause/), with an `IdleDetected` event. Or `PausedEarly`, naming the hours forecast quiet | With `pauseEarly`, step 3 goes on to step 4 as if the clock had run out, when: * the last activity was at least 20 minutes ago, * the forecast is confident every hour until `idleAfter` runs out is quiet, and at least this hour and the next, * and a request would wake the workload through the doorman once it’s paused. While step 4 holds a pause off, `IdleVetoed` is `True` with reason `ForecastExpectsDemand`, its message naming the hour. An `IdleVetoed` event marks each veto’s start. After an hour far quieter than forecast, as on a holiday, the forecast doubts what it expects. For the next hour it holds nothing back ([Anomaly detection](https://docs.napwake.dev/latest/concepts/forecasting/#anomaly-detection)). It never blocks a pause until it’s confident, so a workload with no history is left to the clock. | Case | What changes | | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | At zero replicas, not by Napwake | Not checked. It’s already off, and [left that way](https://docs.napwake.dev/latest/guides/pause/#workloads-already-at-zero) | | No `idlePolicy` | None of this runs. It pauses only when someone asks | | A [pause request](https://docs.napwake.dev/latest/guides/pause/#pause-now) (`kubectl napwake pause`) | The clock runs out at once | | Skipped for a request | Steps 1 and 3, and the hour after a GitOps tool undid its last pause | | Still holding a request up | Steps 2 and 5. Step 4 too, unless the request has `napwake.dev/pause-overrides-forecast: "true"`, as `kubectl napwake pause --yes` sets | | A request held back | It’s answered with the reason | | `dryRun: true` | `Idle`, with the `IdleDetected` or `PausedEarly` event prefixed `[dry-run]`, but nothing changes. Activity sets it back to `Running` ([Dry run](https://docs.napwake.dev/latest/guides/dry-run/)) | ## Paused while in use Napwake can’t see requests to an awake workload. One in steady light use, under its CPU threshold, can look idle and be paused while people use it. The next request wakes it, with a cold start. A pause is wrong when the workload’s own use undoes it soon after it begins. Soon means within `idleAfter` or 15 minutes, whichever is shorter. Any of these undoes it: * a request, or a person’s click for a workload that [asks first](https://docs.napwake.dev/latest/concepts/wake-on-request/#asking-before-waking) * a [wake request](https://docs.napwake.dev/latest/guides/pause/#wake-now) * an activity annotation One that comes while the workload is still pausing [calls the pause off](https://docs.napwake.dev/latest/guides/pause/#a-request-calls-the-pause-off). That pause was wrong too. After a wrong pause, the idle clock waits longer before the next. Each wrong pause in a row doubles the wait, up to `idleAfter` plus an hour: | Wrong pauses in a row | Wait with `idleAfter: 5m` | Wait with `idleAfter: 1h` | | --------------------- | ------------------------- | ------------------------- | | 0 | 5 minutes | 1 hour | | 1 | 10 minutes | 2 hours | | 2 | 20 minutes | 2 hours | | 3 | 40 minutes | 2 hours | | 4 or more | 1 hour 5 minutes | 2 hours | A pause that lasts the window ends the wait. So do these, which no pause can last through: * dry-run * protecting the workload * removing its `idlePolicy` * ignoring it * its target going A would-be pause in dry-run never waits longer. The count is kept in `status.idleWait`, so a restart keeps it. The wait only ever delays a pause. So the longer wait doesn’t fix anything by itself. A workload quiet overnight has a pause that holds, and the next working day starts again at `idleAfter`. Its wrong pauses come back every working day until you fix the cause, about 10 a day with `idleAfter: 5m` and steady light use. Behind the doorman, the forecast learns the hours when a request, a click, a wake request or an activity annotation undid a pause. Once it acts, it holds pauses off in those hours ([What an hour records](https://docs.napwake.dev/latest/concepts/forecasting/#what-an-hour-records)). [What Napwake tells you](#what-napwake-tells-you) says what to change. Each costs a user little. If what wakes the workload comes while it’s still pausing, the pause is [called off](https://docs.napwake.dev/latest/guides/pause/#a-request-calls-the-pause-off): its pods carry on, or are scaled back up if they’d begun to stop. If a request wakes it after it reached zero, that request waits for a cold start. The doorman holds it through the wake, as it holds any request to a paused workload. These don’t make a pause wrong, since Napwake didn’t misjudge the workload’s use: * a pause someone asked for * the forecast waking it ahead of demand * a Prometheus activity query * a wake for an awake dependent that uses it * a wake for a paused dependent Napwake [hands back](https://docs.napwake.dev/latest/guides/pause/#when-napwake-lets-go), as when its ManagedWorkload is deleted ### What Napwake tells you A `PausedWhileInUse` warning event says how soon the pause was undone. It also says how long the clock waits now, and what to change. The `PausedWhileInUse` condition says the same until a pause holds, or the wait ends otherwise. [`kubectl napwake status`](https://docs.napwake.dev/latest/getting-started/kubectl-plugin/#see-what-napwake-is-doing) lists it under Needs attention. 
```text
a request came 40 seconds after it paused, so it was in use: it now waits 10 minutes without activity
before pausing, not 5 minutes, until a pause holds. It used up to 0.6% of its CPU requests while in use,
and up to 0.2% idle: try napwake.dev/cpu-threshold: "0.4"
```
 The suggested number comes from the CPU Napwake measures through each stretch the clock counts as idle: * A wrong pause shows what the workload uses in use. That’s the most in the stretch before it. * A pause that holds shows what it uses idle. That’s the most in the 15 minutes before it, or `idleAfter` if shorter. Napwake keeps the most over the last week. Napwake suggests a threshold when the CPU in use is at least twice the idle CPU, and 0.2 points more. It’s halfway between, to a tenth. A workload you opted in with the label is told the annotation, and one you wrote the field. Otherwise CPU can’t tell its use from its idle. Then Napwake suggests a [Prometheus query](https://docs.napwake.dev/latest/guides/prometheus-signals/#example-queries) that counts its requests. Until a pause has held, it hasn’t measured idle use, and says so rather than guess. 
```yaml
status:
  idleWait:
    wrongPauses: 1
    lastWrongPause:
      pausedAt: "2026-10-26T09:02:11Z"
      after: 40s
      by: request          # request, click, wakeRequest or annotation
      from: 10.4.1.7
      inUseCPU: "0.6"
    idleCPU: "0.2"
    idleCPUAt: "2026-10-25T17:06:00Z"
```
 `napwake_wrong_pauses_total` counts wrong pauses, by workload. Dry-run never pauses, so its would-be pauses aren’t judged. ## When a source can’t be read Napwake never pauses while a source can’t be read. Without that data, a busy workload looks idle. Nor does that time count as idle. * A check that can’t read a source isn’t watching. A source out for longer than the [allowed gap](#restarts-and-outages) restarts the clock (`lastActivitySource: unobserved`). * Once the source is back, an `Unobserved` event says so. A pause then needs a full `idleAfter` in which every source saw nothing. * A shorter blind spot leaves the last activity alone. One is the minute before a woken workload’s pods have metrics. * A Prometheus query may come back saying “no requests in the last 5 minutes”. That doesn’t make the hour before look idle. For CPU, the `MetricsAvailable` condition says why, and for queries, `PrometheusAvailable`. ## Restarts and outages The clock lives in `status.activity`, so it survives operator restarts. An outage can delay a pause, but never cause one. 
```yaml
status:
  activity:
    lastActivityTime: "2026-10-02T09:14:00Z"
    lastActivitySource: cpu    # created, woke, request, cpu, rollout, annotation, prometheus, unobserved, or scaled-up
    pauseAt: "2026-10-02T10:14:00Z"
    lastEvaluatedTime: "2026-10-02T09:41:00Z"
```
 If the operator stops watching for a while, it can’t know what happened. So an awake workload’s clock restarts when it watches again (`lastActivitySource: unobserved`). An `Unobserved` event says how long the gap was: | The gap | The `Unobserved` event says | | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | | The operator didn’t check it | `Napwake wasn't watching for 9 minutes, so its idle clock starts again` | | A source was out | `Napwake couldn't read its activity for 9 minutes, so its idle clock starts again` | | A restart, or a change of leader | `the operator restarted, or another took over, so its idle clock starts again; it wasn't watching for up to 4 minutes` | * The gap allowed is half of `idleAfter`, at least 2 minutes (two missed checks), at most 7. * A restart or a change of leader always restarts an awake workload’s clock, however recently it was written. * The event comes with the first check that can read every source. * A gap or a restart isn’t activity, so a paused workload stays paused. In dry-run, a would-be pause goes on, as the real pause would ([Dry run](https://docs.napwake.dev/latest/guides/dry-run/#what-happens-in-dry-run)). * A restart can delay a pause by up to `idleAfter`, but never brings one forward. ## Waking up | While it’s paused | | | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | | A request reaches one of its Services | Wakes. The request is held while it starts, then answered ([Wake on request](https://docs.napwake.dev/latest/concepts/wake-on-request/)) | | A `last-activity`, `last-request` or `active-until` annotation, on the ManagedWorkload or its target, changes to an RFC 3339 time | Wakes, whatever time it states, so a clock behind the operator’s can’t lose a wake | | `kubectl napwake wake`, or a tool setting [`napwake.dev/wake-requested`](https://docs.napwake.dev/latest/guides/pause/#wake-now) on the ManagedWorkload, such as a portal’s “start environment” button | Wakes, whatever the wake setting, with a `WakeRequested` event. The tool reads the answer in the `WakeRequest` condition | | An annotation set before the pause, even to a later time | Stays asleep. The pause records the annotations as they stood, and only a change counts | | A [Prometheus activity query](https://docs.napwake.dev/latest/guides/prometheus-signals/#while-the-workload-is-paused) shows activity. Queries run about once a minute, as while awake | Wakes. One active as a [requested pause](https://docs.napwake.dev/latest/guides/pause/#pause-now) began must go quiet first, so it doesn’t undo the request | | A query can’t be evaluated | Never wakes it | | `autoResume: true`, and a confident forecast (`dailyPhase: Active`) predicts above `cpuThreshold` this hour, or the next from 15 minutes before | Wakes, ready before people arrive. With `pauseEarly` and a quiet forecast, the pause can come 20 minutes after the wake. `lastActivitySource` says what woke it: | `lastActivitySource` | Woken by | | -------------------- | ---------------------------- | | `request` | A held request | | `prometheus` | An activity query | | `scaled-up` | Something else scaling it up | | `woke` | Anything else | Next * [Wake on request →How a request wakes a paused workload.](https://docs.napwake.dev/latest/concepts/wake-on-request/) * [Forecasting →How the forecast holds off a pause, or brings it forward.](https://docs.napwake.dev/latest/concepts/forecasting/)

# Lifecycle

> Every ManagedWorkload moves through a defined set of phases.

1. Awake Running Active. Its activity clock is checked on each reconcile. 2. No activity for `idleAfter`, or a pause asked for 3. Awake Idle Napwake pauses it, or in dry-run reports the pause it would make. 4. At once, unless held back 5. Asleep Pausing What the pause will change is recorded. Then it's scaled to zero and its pods stopped. 6. 7. Asleep Paused At zero replicas. 8. A request, activity, or `autoResume` 9. Waking up Resuming Its previous replica count is being restored. Running when its pods are Ready, or when Napwake stops waiting for those that aren't The operator moves a workload on from its activity, its forecast, and pauses asked for with `kubectl napwake pause`. * A new ManagedWorkload has no phase until its first reconcile sets `Running`. `kubectl napwake status` shows `creating`. The API accepts `Creating` but never sets it. * A workload a person, a pipeline, KEDA or its HPA scaled to zero stays `Running`, with the `ScaledToZero` condition. Napwake only pauses what’s running, and only wakes what it paused. See [Workloads already at zero](https://docs.napwake.dev/latest/guides/pause/#workloads-already-at-zero). ## Transition triggers ### Automatic | Transition | When | | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Running → Idle | No activity for `idleAfter`. Or, with [`pauseEarly`](https://docs.napwake.dev/latest/concepts/forecasting/#pausing-early), for 20 minutes before hours a confident forecast expects quiet. And nothing may [hold it up](https://docs.napwake.dev/latest/concepts/idle-detection/#the-decision) | | Idle → Pausing | At once, unless it’s in dry-run, or a GitOps tool undid its last pause within the hour | | Idle → Running | Activity resumes while dry-run or a GitOps tool’s undoing holds the pause off. Or it’s scaled to zero outside Napwake | | Paused → Resuming | A request to its Service, or with [`wake.mode: Ask`](https://docs.napwake.dev/latest/concepts/wake-on-request/#asking-before-waking) a person’s click on **Wake it**. A new `napwake.dev/wake-requested` value. A change to an activity annotation since the pause. A [Prometheus activity query](https://docs.napwake.dev/latest/guides/prometheus-signals/#while-the-workload-is-paused) showing activity. `autoResume` ahead of forecast demand. Dry-run turned on | | Pausing → Resuming → Running | Whatever would wake it once paused comes as it pauses, which [calls the pause off](https://docs.napwake.dev/latest/guides/pause/#a-request-calls-the-pause-off). A `PauseCancelled` event says what came. It’s then scaled back up if its pods had begun to stop | | Paused → Running | Something else scales it up ([GitOps tools](https://docs.napwake.dev/latest/guides/gitops/)), or Napwake [lets go of it](https://docs.napwake.dev/latest/guides/pause/#when-napwake-lets-go). Also from `Pausing`, once it’s at zero (`status.pause.pausedAt`) while its pods stop. It isn’t scaled back down | | Resuming → Running | Every replica it was restored to is Ready, or Napwake stops waiting (below). Scaled back to zero by something else after the resume scaled it up (`status.pause.resumedAt`), it’s left off with `ScaledToZero` | The resume’s wait starts once its `waitForReady` [dependencies](https://docs.napwake.dev/latest/concepts/dependencies/) serve. Napwake stops waiting 2 minutes after the first replica is Ready. With none Ready, it stops at the Deployment’s `progressDeadlineSeconds` after the scale-up. That’s 10 minutes by default. A StatefulSet has no such field, so it gets 10 minutes too. Stopping short sets `ResumeIncomplete`, and [Resume](https://docs.napwake.dev/latest/guides/pause/#resume) has what follows. ### On request | Transition | When | | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Running or Idle → Pausing → Paused | [`kubectl napwake pause`](https://docs.napwake.dev/latest/guides/pause/#pause-now), which sets a new `napwake.dev/pause-requested` value | | Running → Idle | The same in dry-run, as a would-be pause | | Paused → Resuming → Running | [`kubectl napwake wake`](https://docs.napwake.dev/latest/guides/pause/#wake-now), which sets a new `napwake.dev/wake-requested` value, whatever the wake setting. Or any automatic wake. A requested pause wakes like any other | | Pausing → Resuming → Running | `kubectl napwake wake` as it pauses, which calls the pause off, with a `PauseCancelled` event | | Idle → Running | The same in dry-run, ending a would-be pause. Awake, a wake request restarts the idle clock | A request runs the idle clock out at once, and the rules of an idle pause apply. The wait after a GitOps conflict, or a [pause undone at once](https://docs.napwake.dev/latest/guides/managed-workload/#a-pause-undone-at-once), doesn’t hold it back. A forecast expecting demand within the hour declines it, saying when, unless the request overrides the forecast. ## Idempotency Every lifecycle operation is idempotent. The operator can crash and restart at any point without leaving a workload inconsistent. Before anything is scaled, the status write that enters `Pausing` records what the pause changes in `status.pause`. That’s `previousReplicas`, the KEDA ScaledObject, and its own `paused-replicas` value. So: * Wherever a restart or a conflicting write interrupts a pause, it’s finished or undone from the record. * Resuming restores the recorded replica count, not a hardcoded value. * Pausing an already-paused workload does nothing. Before scaling, the record is also copied to the target’s `napwake.dev/paused-from` annotation, until it’s handed back. If the ManagedWorkload loses its status while paused, by a restore without status or being created again: | It finds | Then | | ------------------------------------------------ | ------------------------------------------------------- | | The copy, and the workload still at zero | Back to `Paused` (`PauseRecovered`) | | The copy, and the workload scaled up since | Released (`PauseRecovered`) | | Neither, while `Pausing`, `Paused` or `Resuming` | Nothing was scaled. `Running` again (`PauseRecordLost`) | `spec.target` can’t change once set, so a paused target is never left at zero. To manage another workload, create another ManagedWorkload. ## Status conditions A ManagedWorkload’s conditions report what the operator found, such as what holds it awake or why it won’t pause. [`IdleVetoed`](https://docs.napwake.dev/latest/reference/conditions-and-events/#condition-idlevetoed) and [`HeldByDependents`](https://docs.napwake.dev/latest/reference/conditions-and-events/#condition-heldbydependents) hold a pause off. [`ScaledToZero`](https://docs.napwake.dev/latest/reference/conditions-and-events/#condition-scaledtozero) leaves a workload off. [`ResumeIncomplete`](https://docs.napwake.dev/latest/reference/conditions-and-events/#condition-resumeincomplete) says a resume stopped waiting. [Conditions and events](https://docs.napwake.dev/latest/reference/conditions-and-events/#status-conditions) lists every condition, with each reason. ## Events Each user-visible change emits one event, as it happens, shown by `kubectl describe`. The phases above show as [`IdleDetected`](https://docs.napwake.dev/latest/reference/conditions-and-events/#event-idledetected), [`Paused`](https://docs.napwake.dev/latest/reference/conditions-and-events/#event-paused) and [`Resumed`](https://docs.napwake.dev/latest/reference/conditions-and-events/#event-resumed). What woke it shows as a reason for each cause, such as [`WokenByRequest`](https://docs.napwake.dev/latest/reference/conditions-and-events/#event-wokenbyrequest) for a request. [Conditions and events](https://docs.napwake.dev/latest/reference/conditions-and-events/#events) lists every event, by what it’s about. # Wake on request

> How the first request wakes a paused workload, held by the doorman until a pod is Ready.

A request reached staging while it was paused. The doorman holds it while staging starts, then passes it to the first Ready pod. A paused workload has no pods, so nothing answers its Service. The first request wakes it. The doorman holds the connection until a pod is Ready, then passes it through. The caller usually sees one slow response ([the exceptions](#what-the-caller-sees)). The wait is as long as the pods take to start and pass their readiness probe. For the [Quickstart’s](https://docs.napwake.dev/latest/getting-started/quickstart/#6-wake-it-with-a-request) nginx, that’s a second or two. On a public URL, the doorman can [ask before waking](#asking-before-waking) instead. Then only a person’s click wakes it. * Default On for every workload Napwake pauses on its own, with nothing to configure * On a public URL `ask`: a browser gets a **Wake it** button, and crawlers, scanners and API calls wake nothing * Protocols Any TCP, such as HTTP, gRPC, Postgres and Redis * Holds a request Up to `wake.maxWait`, 2 minutes by default * Browsers A waking-up page that reloads every 3 seconds ## How it works The doorman is a small proxy, its own Deployment beside the operator, with two replicas and a PodDisruptionBudget. 1. Asleep · paused Routed to the doorman Its Services point at the doorman. 2. A caller connects and sends something 3. Waking up · resuming Held, and woken The doorman holds the connection and wakes the workload. 4. A pod is Ready 5. Awake · running Passed through A Ready pod gets the connection. | When | What happens | | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | The workload starts to pause | The operator adds an EndpointSlice, one per IP family, to each Service that selects its pods. It points at the doorman, on a port of its own (20000-29999). The Service, ClusterIP and DNS name don’t change, so callers and Ingresses need no changes. IPv4, IPv6 and dual-stack all work. The slice is in place before the pods stop, so no request is refused as they do ([What happens in a pause](https://docs.napwake.dev/latest/guides/pause/#what-happens-in-a-pause)) | | A connection arrives | If a pod of the Service is already Ready, it goes straight there. That happens while it’s still pausing or already waking, or when another workload’s pods serve the Service. While it’s pausing, a request passed on that would wake it [calls the pause off](https://docs.napwake.dev/latest/guides/pause/#a-request-calls-the-pause-off). A pod that doesn’t answer within a quarter of a second has the next tried beside it. One that leaves the EndpointSlices as it’s tried, as a pod the pause stops does, is given up. With no Ready pod, or none left, the doorman waits for the caller to send something | | The caller sends something | The doorman holds the connection and sets `napwake.dev/last-request` on the ManagedWorkload, which wakes it like an [activity annotation](https://docs.napwake.dev/latest/concepts/idle-detection/#activity-annotations). A `RequestHeld` event from the doorman names the Service, and the operator’s `WokenByRequest` says a request woke it. Once Running, the clock shows `lastActivitySource: request` | | A pod is Ready | The doorman, watching the Service’s own EndpointSlices, passes the held connection to a Ready pod, with the bytes already sent | | The workload is `Running` | The operator removes the doorman’s EndpointSlices. For 30 seconds the doorman still passes stray connections to Ready pods, waking nothing, while kube-proxy and load balancers catch up | The doorman works on TCP connections, not HTTP requests.  ### Readiness probes The doorman lets a held request through once a pod is Ready. Ready comes from the readiness probe. Without one, a pod is Ready when its containers start, often before the app can serve. The request then gets whatever the app answers, such as a `503`. Give the app a probe that passes only once it can serve. If the app isn’t listening yet, the doorman retries every second until `maxWait`. deployment.yaml 
```yaml
spec:
  template:
    spec:
      containers:
        - name: api
          readinessProbe:
            httpGet:
              path: /ready   # answers 200 only once the app can serve requests
              port: 8080
            periodSeconds: 2
```

The `WakeOnRequest` condition says so, and a `NoReadinessProbe` warning event points here, once each pause | ### What wakes a workload, and what doesn’t | The caller | What happens | | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | | Sends bytes, such as an HTTP request, a TLS handshake or a database protocol’s first message | Held. ```

That’s the `503`s and closed connections, not a person shown the page, nor probes and health checks. It’s a count only, with nothing of the requests themselves, no paths, addresses or headers. It’s in the ManagedWorkload’s status, brought up to date about once a minute. It covers the current pause, or the last one once the workload is awake. 
```yaml
status:
  turnedAway:
    pausedAt: "2026-10-23T18:04:12Z"
    requests: 312
```

 ## How long a connection is held The doorman holds a connection for up to `wake.maxWait`. That’s 2 minutes by default, and at most 1 hour, the most the ManagedWorkload accepts. With no Ready pod by then, it closes the connection. The wake carries on, so a retry a little later succeeds. With the label, set the annotation `napwake.dev/wake-max-wait: "5m"` instead. 
```yaml
spec:
  wake:
    maxWait: 5m     # a slow starter, such as a database replaying its log
```
 Callers time out too. Most HTTP clients wait at least 30 seconds, and browsers minutes. A proxy can give up sooner. ingress-nginx waits 60 seconds for an answer by default. Then it tries again, up to 3 tries in all, unless the request is a `POST` or `PATCH`: | With ingress-nginx’s defaults, the workload is Ready | A `GET` gets | A `POST` or `PATCH` gets | | ---------------------------------------------------- | -------------------------------------- | ------------------------ | | Within 60 seconds | Its answer | Its answer | | Within 3 minutes | Its answer, on the second or third try | A `504` at 60 seconds | | Later | A `504` at 3 minutes | A `504` at 60 seconds | Each try reaches the same doorman pod or another, which holds it. Each try ingress-nginx gives up on is counted as `canceled` ([Metrics](https://docs.napwake.dev/latest/reference/metrics/#doorman)). A client that gives up first gets no answer, and ingress-nginx logs a `499`. For a slower starter, raise the timeout to match `maxWait`. The doorman then holds each request once, until a pod is Ready or `maxWait` runs out: 
```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-read-timeout: "120"
```
 Set it higher than `maxWait`, and the doorman lets go first. A `GET` is then tried again, and a `POST` gets a `502`. ### A wake that outlasts ingress-nginx’s timeout Napwake reads how long ingress-nginx waits in front of a workload, and says once a wake has taken longer. Until then, `kubectl napwake status` notes each Ingress in front that waits less than `maxWait`: 
```text

  staging/my-api   Ingress my-api waits 60s, maxWait is 120s
```

That holds however long the connection is quiet, and after the workload’s Service sends new connections to its pods again. A database pool that connects while its database wakes keeps its connections through the doorman. Closing one would fail the pool’s next query on it. Some apps answer that with an error, such as PostgREST’s `503`. So the doorman sets no limit of its own. The `NapwakeDoormanWakesFailing` alert fires when a workload’s held connections keep timing out or failing. ## The wake setting It says what wakes a paused workload through the doorman. `request`, the default, is any request. `ask` is only a person’s click ([Asking before waking](#asking-before-waking)). | For | Set | Values | | --------------------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------- | | A ManagedWorkload | `spec.wake.mode` | `Request`, the default, or `Ask` | | A workload opted in with the label | `napwake.dev/wake` on it, or on its namespace | Exactly `"request"` or `"ask"` | | Labelled workloads whose own and namespace’s annotations don’t set it | The Helm value `defaults.wake`, which sets the operator flag `--default-wake` | `request`, the default, or `ask` | The workload’s annotation wins, then its namespace’s, then `defaults.wake`.  ## GKE container-native load balancing (NEGs) The forwarder is optional and off by default. Turn it on if people reach your paused environments through a GKE Ingress on NEGs, or a GKE Gateway: 
```yaml
doorman:
  negForwarder:
    enabled: true
```
 GKE’s NEG controller accepts only endpoints whose pods are in the Service’s own namespace. So a Service in NEGs can’t point at the doorman. GKE uses NEGs for an Ingress’s Services by default on VPC-native clusters, and always for a Gateway’s. Services neither uses wake workloads without the forwarder. ### What it runs While a workload with a Service in NEGs is paused, the operator runs a forwarder beside it. That’s a Deployment in its namespace, `napwake-forwarder-<workload>`. | | The forwarder | | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | What it does | It stands in for the workload’s pods in that Service’s endpoints, which GKE accepts, since it’s in the Service’s namespace. It passes every connection to the doorman, bytes untouched, and the doorman holds it and wakes the workload. A doorman pod that doesn’t answer within a quarter of a second, as one that has just gone in a rollout or a drain, has the next tried beside it. The workload’s other Services, those no NEG uses, go to the doorman directly | | Lifetime | The operator deletes it a minute after the workload is `Running` and its route has drained. The ManagedWorkload owns it, so deleting the ManagedWorkload deletes it too | | Size | Two small pods by default, spread across nodes ([sizes](https://docs.napwake.dev/latest/reference/helm-values/#doorman)). A node drain then doesn’t cut the workload off while GKE registers a new pod. They run only while the workload is paused | | Access | The operator’s image, as the namespace’s `default` ServiceAccount without its token, with no access to the API server. Its pods meet the Pod Security Standards’ restricted level, and keep Istio’s and Linkerd’s sidecars out. It carries `napwake.dev/ignore`, so Napwake doesn’t manage it in a namespace opted in with the label | | Ports | The Services’ target ports, which GKE’s firewall rules let Google’s load balancers reach. Below 1024, it sets the `net.ipv4.ip_unprivileged_port_start` sysctl, which the restricted level allows, rather than run as root | | Readiness | Ready only while it reaches the doorman on every port it forwards. It finds the doorman through a headless Service the chart adds, `napwake-doorman-pods` for a release named `napwake` | To see it: 
```bash
kubectl get deployments -n preview-42 -l app.kubernetes.io/name=napwake-forwarder
kubectl get endpointslices -n preview-42 -l napwake.dev/forwarded=true
```
 A route through the forwarder shows `forwarded: true` in the ManagedWorkload’s `status.doorman`. ### Health checks behind NEGs Keep the backend service’s health check on the traffic port, over plain HTTP. A GKE Ingress sets that up for an HTTP backend. Google’s load balancer now checks the forwarder, which passes the check to the doorman. `GoogleHC/` gets `200 OK`, as on every route, and every other checker `503`. HTTPS and HTTP/2 checks can’t be read here either, so they wake the workload every run. A port of its own fails here, since the forwarder listens only on the ports it routes. The load balancer then sends nothing on. ### Timeouts behind NEGs For a slower starter, raise the backend service’s timeout to match `wake.maxWait`. Google’s load balancer waits 30 seconds for a backend by default, and only browsers get an answer at once. On a GKE Ingress, use a BackendConfig, which the Service names in its `cloud.google.com/backend-config` annotation as `'{"default": "slow-start"}'`. On a GKE Gateway, set `spec.default.timeoutSec` in a GCPBackendPolicy. 
```yaml
apiVersion: cloud.google.com/v1
kind: BackendConfig
metadata:
  name: slow-start
  namespace: preview-42
spec:
  timeoutSec: 120
```
 ### Network policies behind NEGs The chart’s doorman NetworkPolicy admits forwarders from any namespace, by their labels, `app.kubernetes.io/name: napwake-forwarder` and `napwake.dev/operator` naming Napwake’s namespace. Anyone who can create pods can give them those labels. So they can reach the routing ports, as a caller in `ingressFrom` can. With a default-deny policy in the workload’s namespace, let whatever reaches the workload reach the forwarder. That includes Google’s load balancers and health checks, from `130.211.0.0/22` and `35.191.0.0/16`. Let the forwarder reach the doorman and DNS. If apps in the cluster call the Service too, add them to `ingress.from`. 
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-napwake-forwarder
  namespace: preview-42
spec:
  podSelector:
    matchLabels: {app.kubernetes.io/name: napwake-forwarder}
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - ipBlock: {cidr: 130.211.0.0/22}
        - ipBlock: {cidr: 35.191.0.0/16}
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: napwake-system}
          podSelector:
            matchLabels: {control-plane: doorman}
      ports:
        - {port: 20000, endPort: 29999, protocol: TCP}
    - ports:
        - {port: 53, protocol: UDP}
        - {port: 53, protocol: TCP}
```
 ### Limits behind NEGs | When | What happens | | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Right after a pause | GKE takes a while, usually under a minute, to register the forwarder’s pods and see them pass health checks. Until then, requests through the load balancer can get a `502`, as after any scale-down. The Service can also show GKE’s warning event `SyncNetworkEndpointGroupFailed`, `endpoint count from endpointPodMap cannot be zero`. That’s for the moment between the workload’s pods going and the forwarder’s arriving, and GKE retries within seconds | | After a wake | The Service goes back to the workload’s pods as soon as one is Ready. While the route drains, for 30 seconds, the forwarder passes what still reaches it to the doorman, and on to the workload | | The caller’s address | The doorman sees the forwarder’s. So dependencies aren’t [learned](https://docs.napwake.dev/latest/concepts/dependencies/#learned-dependencies) from requests through it, and the per-source [limits](#limits) count each forwarder pod as one source. Through a load balancer, the caller is one of Google’s proxies anyway | | Images from a private registry | The forwarder pulls the operator’s image in the workload’s namespace, as its `default` ServiceAccount. A mirror that needs a pull secret needs it there too. GKE nodes pull from Artifact Registry in their own project without one | | Turning it off | Running forwarders stay, since the operator may no longer delete them. Remove them with `kubectl delete deployments -A -l app.kubernetes.io/name=napwake-forwarder` | | The Kustomize manifests | Set it up by hand. Run the operator with the `--neg-forwarder` flags ([Configuration](https://docs.napwake.dev/latest/reference/configuration/#operator-flags)). Grant it `create` and `delete` on Deployments, and add a headless Service selecting the doorman’s pods | ## Network policies The doorman connects to woken pods directly, from Napwake’s namespace. If a workload’s namespace has a default-deny NetworkPolicy, allow ingress from the doorman. Callers reach the doorman on ports 20000-29999, so a default-deny policy in Napwake’s namespace must allow those too. 
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-napwake-doorman
  namespace: preview-42
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: napwake-system}
          podSelector:
            matchLabels: {control-plane: doorman}
```
 ### Restricting who can reach the doorman The doorman is a way in to every paused workload Any client that reaches a doorman pod can reach every routed, paused workload, in any namespace, on its Service ports. A workload’s own NetworkPolicy sees the doorman as the source. So a policy that admits the doorman admits everyone who can reach it. The rate limits slow a port scan through the doorman, but don’t stop one. The chart’s NetworkPolicy (`networkPolicy.enabled`, off by default) leaves the routing ports open until you say who may use them. List your paused workloads’ real callers in `doorman.networkPolicy.ingressFrom`. Such callers include your ingress controller’s namespace, and the namespaces whose apps call paused services: 
```yaml
networkPolicy:
  enabled: true
doorman:
  networkPolicy:
    ingressFrom:
      - namespaceSelector:
          matchLabels: {kubernetes.io/metadata.name: ingress-nginx}
      - namespaceSelector:
          matchLabels: {team: checkout}
```
 | | How the chart’s policy treats it | | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Each `ingressFrom` entry | A NetworkPolicy peer, so `podSelector` and `ipBlock` work too. Everyone else is refused before reaching the doorman | | The operator’s own pods | Added by the chart. They connect to each doorman pod before a pausing workload’s Services are sent to it, to check it’s listening | | The doorman’s metrics port | Open to namespaces labelled `metrics: enabled` | | `ingressFrom` without `networkPolicy.enabled` | Refused at install, since it would create no policy and leave the doorman open | | A policy of your own beside the chart’s | Don’t add one. NetworkPolicies add up, so the chart’s open routing ports would still admit everyone | | Traffic from outside the cluster, through a NodePort or LoadBalancer Service | It usually arrives from a node’s address, since kube-proxy rewrites the source when it forwards to another node. Selectors don’t match nodes, so `ingressFrom` refuses it. Add your nodes’ CIDRs as an `ipBlock` entry, or the load balancer’s addresses if it keeps the client’s | | A routed Service with `externalTrafficPolicy: Local` | It keeps the client’s address. External callers then reach the doorman only through nodes that run a doorman pod ([Compatibility](https://docs.napwake.dev/latest/reference/compatibility/#service-proxies)) | Limit the doorman’s egress too. It dials only Pod-backed endpoints of EndpointSlices that the EndpointSlice controller manages. It never dials loopback, link-local or cloud metadata addresses ([Security](https://docs.napwake.dev/latest/reference/security/#the-doorman-is-a-way-in-to-paused-workloads) has the rules). An egress policy enforces the same bounds in the network. The chart can create one that allows only your pod CIDRs and the API server: 
```yaml
doorman:
  networkPolicy:
    egress:
      enabled: true
      podCIDRs: [10.244.0.0/16]
      apiServer: [172.18.0.2/32]   # kubectl get endpointslices -n default -l kubernetes.io/service-name=kubernetes
      apiServerPorts: [443, 6443]
```
 List every IP family your cluster uses, and the node CIDRs too if a routed workload uses `hostNetwork`. `apiServer` takes the API server’s endpoint addresses, not the `kubernetes` Service’s ClusterIP, since policies apply after the Service is resolved. Two admission policies are on by default (`doorman.admissionPolicy.enabled`), in the Kustomize manifests too. One lets the doorman’s ServiceAccount change only `napwake.dev/last-request` and `napwake.dev/last-request-from` on a ManagedWorkload. It may also set `napwake.dev/turned-away`, where it counts what it [turned away](#what-it-turns-away). The other lets no one else set the first two. Besides those, the doorman reads one Secret, its own [wake key](#the-wake-it-button), by name, and writes it once to fill it. So only the doorman can say a request woke a workload, or where it came from ([Security](https://docs.napwake.dev/latest/reference/security/#the-doorman-is-a-way-in-to-paused-workloads)).
